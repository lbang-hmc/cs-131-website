## Basic Values and Types

In Haskell, **values** are specific pieces of data, and **types** categorize those values. A few basic types you'll use constantly:

| Type | Example values |
|---|---|
| `Integer` | `1`, `2`, `100000000000`, `-42` |
| `Double` | `3.14`, `3.2831`, `-2.718` |
| `Bool` | `True`, `False` |
| `Char` | `'a'`, `'z'` |
| `String` | `"hello"`, `"world"` |

**All type names start with an uppercase letter — but not every uppercase name is a type.** That's a one-directional rule, worth keeping in mind.

Haskell also has two ways to group values together, and the distinction matters:

- **Lists** (`[ ]`) are *homogeneous* — every element must share the same type — and can be any length: `[1, 2, 3, 4] :: [Integer]`.
- **Tuples** (`( )`) are *heterogeneous* — elements can have different types — but have a fixed length baked into their type: `(True, 0.5) :: (Bool, Double)`.

The usual operators work as you'd expect: arithmetic (`+`, `-`, `*`, `/`), comparison (`==`, `/=`, `>`, `<`, `>=`, `<=`), and `++` to concatenate strings and lists.

### Reading a Type Error

Type errors are where a lot of beginning-Haskell frustration lives, so it's worth learning to read one on purpose. Here's a real one:

```
<interactive>:27:14: error:
    • Couldn't match expected type ‘Bool’ with actual type ‘Char’
    • In the expression: 'a'
      In the expression: [True, True, 'a']
      In an equation for ‘it’: it = [True, True, 'a']
```

!!! question "Think about it"
    Before reading on: what is this error actually telling you, line by line? What expression caused it, and why?

    ??? note "Decoding it"
        The offending code is `[True, True, 'a']` — a list mixing `Bool`s and a `Char`. Since lists are homogeneous, Haskell picked the type of the first elements (`Bool`) as what the whole list *should* be, then choked when it hit `'a'`, a `Char`. Read bottom-up: "I was checking the type of `it = [True, True, 'a']` … which contains the subexpression `[True, True, 'a']` … which contains the subexpression `'a'` … and `'a'` isn't the `Bool` I expected." The fix: make every element the same type.

## Calling Functions

Haskell is a *functional* programming language, so naturally, calling functions is easy:

```haskell
sqrt 4        -- square root of 4
show 42       -- converts 42 to a String
min 0 42
max 100 (42 + 1)
not True
```

A few habits worth building early:

!!! tip "Watch out: parenthesize sub-expressions"
    `max 100 42 + 1` does **not** mean `max 100 (42 + 1)` — function application binds tighter than `+`, so this parses as `(max 100 42) + 1`. Wrap arguments that are themselves expressions in parentheses, and it's rarely a mistake to use parentheses liberally until the precedence rules feel natural.

!!! tip "Watch out: `/` vs. `div`"
    `/` is floating-point division; `div` is integer division. `4 / 2` and `div 4 2` are not interchangeable in general — pick the one that matches the type you actually want.

Negative numbers need their own parentheses too, for a related reason: `max -42 42` doesn't parse the way you'd hope. Write `max (-42) 42` instead.

### Booleans and Modular Arithmetic

A few more useful built-ins:

```haskell
True && False   -- False (logical AND)
False || True   -- True (logical OR)
not False       -- True — "not" is a function in Haskell, not a `!` symbol
```

```haskell
mod 2 4   -- 2
mod 4 2   -- 0
mod 4 3   -- 1
```

!!! example
    What time is it seven hours after 10 o'clock, on a 12-hour clock?
    ```haskell
    mod (10 + 7) 12   -- 5
    ```
    Seven hours past 10:00 is 5:00 — exactly what `mod` gives you.

!!! tip "Watch out: chaining `not` with `||`"
    `not False || not True` looks ambiguous at first glance, but it's completely unambiguous to Haskell: function application binds tighter than any operator, so this parses as `(not False) || (not True)`. It's still fine to add the parentheses yourself while this is new — plenty of experienced Haskell programmers would too.

## Variables, Bindings, and Scope

Some vocabulary worth having precisely, because Haskell uses these words in a specific way:

- **Binding** (noun) / **bind** (verb) — associating a variable name with an expression. Similar to *assignment* in imperative languages, but see below for the crucial difference.
- **Value** — the expression a name is bound to.
- **Reference** — using a name in an expression; during evaluation the name is just an alias for what it's bound to.
- **Scope** — the region of the program where a name can be referenced.
- **Lookup** / **resolve** — evaluating a name by finding its value.

```haskell
-- Top-level bindings ("global variables")
x = 21
y = 2 * x
```

Top-level bindings act like global variables — their scope is the whole file (or the rest of your `ghci` session). Variable names are always lowercase in Haskell (recall: type names are always uppercase).

Here's the part that trips people up:

**A scope can bind a name at most once. In other words, all "variables" are constants.**

!!! question "Think about it"
    What's the value of `x` here?
    ```haskell
    x = 24
    x = 41
    x = x + 1
    ```

    ??? note "What actually happens"
        If you put this in a file, you get a compile error — `Multiple declarations of 'x'` — because a name can only be bound once *per scope*. If you type the lines one at a time into `ghci`, the first two "succeed" (each creates a fresh top-level binding that shadows the last), but the third, `x = x + 1`, refers to itself — there's no prior `x` to add one to, just a circular definition — and asking for its value sends `ghci` into an infinite loop. Haskell variables don't mutate; `x = x + 1` isn't an update, it's a (broken) definition.

**Local bindings** work the same way but with a smaller scope, using a `let` expression:

```haskell
let x = 21 in x + x
```

The scope of `x` here is just the body of the `let` — the expression after `in`. Scopes can nest, and Haskell resolves a name starting from the innermost scope outward:

```haskell
let x = 21 in
  let x = 10000 in
    x   -- resolves to the inner x: 10000
```

A `let` can also bind more than one variable, and a later binding can refer to an earlier one from the *same* `let` — a let-bound variable's real scope is the whole `let` expression, bindings and body alike, not just the body:

```haskell
let x = 21
    y = x
in x + y   -- 42
```

Typing a multi-line expression like this directly at the `ghci` prompt needs a little extra syntax — wrap it between `:{` and `:}` on their own lines:

```
:{
let x = 21
    y = 7 * 2
in x + y
:}
```

One thing to watch closely: **indentation is significant** here. The `x` and `y` bindings need to line up directly under each other, or `ghci` will get confused — this trips up almost everyone the first time.

## Working With Files

So far this has all been REPL-only. Haskell source files use a `.hs` extension. A couple of things to know once you move code into a file:

```haskell
-- Single-line comment

{-
   Multiline
   comment
-}
```

Top-level bindings can live in a `.hs` file, but a bare expression on its own can't — files are for definitions. Load a file into `ghci` with `:load <file>` (or `:l <file>` for short); after editing and saving, bring your changes back in with `:reload` (or `:r`).

## Defining Functions

Function definitions name the function, list its parameters, and give a body:

```haskell
successor n = n + 1
average x y = (x + y) / 2
```

```haskell
successor 1    -- 2
average 0 10   -- 5.0
```

A parameter's scope is just the function body — same scoping rule as everything else, just at a smaller size.

### Three Ways to Write a Local Binding

These all compute the same thing, `x² + 1/x²`, and differ only in style:

```haskell
-- Directly
f x = x * x + 1 / (x * x)

-- With a let expression
f x = let value = x * x
      in value + 1 / value

-- With a where clause
f x = value + 1 / value
  where value = x * x
```

The difference between `let` and `where` is scope: a `let` binding's scope is the body of the `let` itself, while a `where` clause's scope is the *entire* function body (including, if you had one, an earlier guard). Which one you reach for is mostly a matter of taste.

### Pattern Matching

This is one of Haskell's superpowers. Compare two ways of writing factorial:

```haskell
-- if/then/else
fact n = if n == 0
         then 1
         else n * fact (n - 1)

-- pattern matching
fact 0 = 1
fact n = n * fact (n - 1)
```

When `fact` is called, Haskell tries each pattern from top to bottom and uses the first one that matches. `fact 0 = 1` only fires when the argument is literally `0`; `fact n = ...` is a catch-all that matches anything else (and, in matching, binds the name `n` to whatever was passed in). You'll be leaning on this constantly once we get to data types with more interesting shapes than numbers.

## Types in Haskell

Haskell is a **statically typed** language: the compiler checks types *before* your program ever runs, and a type error means your program doesn't compile at all — full stop, it can never run with that bug in it. Contrast this with **dynamically typed** languages, where type checks (if any) happen while the program is running, and a type mismatch can crash mid-execution.

A little more vocabulary:

- **Type-safe** — a program with no type errors.
- **Type-check** — the process of determining whether a program has type errors.
- **Type annotation** — information the programmer provides about a type, for clarity or documentation.
- **Type inference** — the compiler's ability to figure out types *without* requiring annotations.

**Haskell is statically typed and uses type inference** — you're usually not required to annotate types, but doing so is still good practice for readability. You can ask `ghci` for the type of anything with `:type <expr>` (or `:t <expr>`).

Function types use `->` to separate parameter types from the result type:

```haskell
successor :: Integer -> Integer
successor n = n + 1

average :: Double -> Double -> Double
average x y = (x + y) / 2
```

Read `::` as "has type." `successor :: Integer -> Integer` reads as "`successor` is a function that takes an `Integer` and results in an `Integer`." For `average`, the two `Double`s before the final arrow are the two parameter types, and the last one is the result.

## What Is Functional Programming?

Remember the first big theme from Module 01.1 — **Functions. Are. Awesome.**? Here's what that actually means in practice:

In **functional programming**, computation happens by *evaluating expressions*. Contrast that with **imperative programming**, where computation happens by *updating state* — variables that change over time, one instruction after another. In **pure** functional programming, expression evaluation is the *only* mechanism for computation — there's no hidden state being quietly mutated behind the scenes.

Haskell is a pure, functional language. That's a big part of why the mental model feels different at first: you're not writing a sequence of steps that change things, you're describing what things *are*, in terms of other things.

## Abstraction: The Essence of CS 131

Watch this transformation:

```haskell
-- Repeated code
2 * 2 + 1
3 * 2 + 1
4 * 2 + 1
5 * 2 + 1
```

```haskell
-- Refactored: factor the repeated shape into a function
f :: Integer -> Integer
f n = n * 2 + 1

f 2
f 3
f 4
f 5
```

Nothing about *what's computed* changed — only how it's expressed. By noticing the repeated shape `_ * 2 + 1` and giving it a name, we turned four separate expressions into one reusable function. That move — spot the pattern, name it, reuse it — is **abstraction**, and it's the through-line of this entire course. You'll see this same move again and again, at every level from small helper functions all the way up to entire language features.
