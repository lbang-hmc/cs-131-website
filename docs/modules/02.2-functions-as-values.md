# Module 02.2: Functions = Values

Module 02.1 got you writing and calling Haskell functions. This module goes one level deeper: *why* Haskell can get away with never letting anything change, what that buys you, and the trick that lets every Haskell function — no matter how many arguments it looks like it takes — secretly take just one. By the end, you'll see functions themselves as ordinary values you can pass around, combine, and build with.

---

## Recap: Expressions and Purity

A little shared vocabulary, since the rest of this module leans on it:

- **Expression** — a "piece of computation," like `1 + 2` or `f 3`.
- **Evaluate** — to try to compute the result of an expression. Evaluation either *terminates* with a result, or *diverges* (runs forever).
- **Side effect** — anything that happens during evaluation that changes state — modifying a variable, printing to the screen.
- **Referentially transparent** — a sub-expression is referentially transparent if you can replace it with its result without changing what the surrounding expression means.
- **Pure expression** — an expression with no side effects. Every pure expression is referentially transparent.
- **Purely functional programming language** — a language (like Haskell) where computation *is* the evaluation of pure expressions, full stop.

Because Haskell is purely functional, a few things follow directly:

- **All "variables" are constants.** No side effects means nothing can quietly change out from under you.
- **Programs are easier to reason about.** If a sub-expression can always be replaced by its value, you can understand a piece of code in isolation.
- **You can't just print things.** Printing is a side effect, and side effects aren't allowed for ordinary expressions. (You *can* do it — but that needs machinery we haven't built yet.)
- **Referential transparency unlocks laziness.** If replacing an expression with its value never changes anything, Haskell is free to delay computing that value until it's actually needed — which is exactly what's coming next.

## Lazy Evaluation

Most languages you've used probably evaluate **eagerly** (also called *strictly*): sub-expressions are computed before they're used.

```haskell
x = 1 + 2        -- 1 + 2 is computed right away; x becomes 3
f (1 + 2) (3 * 4)  -- both arguments are computed before f is even called
```

Haskell instead evaluates **lazily**: an expression isn't computed until its result is actually needed.

```haskell
x = 1 + 2   -- x is bound to the *expression* 1 + 2, not yet to 3

ignoreFirstArgument :: Integer -> Integer -> Integer
ignoreFirstArgument x y = y

ignoreFirstArgument (1 + 2) (3 * 4)   -- (1 + 2) is never evaluated at all!
```

Since `ignoreFirstArgument` never uses its first parameter, `1 + 2` is simply never computed — not "computed and discarded," genuinely never touched. (If you don't intend to reference a parameter at all, you can write `_` instead of naming it: `ignoreFirstArgument _ y = y` is a **wildcard pattern**, meaning "anything can go here, and I'm not going to use it.")

Haskell makes this easy to see directly, using a built-in value called `undefined` — an expression that immediately crashes if you ever evaluate it:

```haskell
x = undefined        -- no error! x is just bound to the *expression* undefined

ignoreFirstArgument undefined 5    -- 5 — undefined is never touched
ignoreFirstArgument 5 undefined    -- *** Exception: Prelude.undefined
```

Binding `x = undefined` produces no error at all, because binding never forces evaluation — only asking Haskell to actually *print* `x` would trigger the crash. The same logic explains `ignoreFirstArgument`: passing `undefined` as the argument that gets thrown away is completely safe, but passing it as the argument that's actually used blows up — not because of *which position* it's in, but because of whether that argument ever gets evaluated.

Laziness also means Haskell only pays for a computation once, no matter how many times you reference the result afterward. Picture a deliberately slow function, `expensive`, that takes a couple of seconds to run:

```haskell
expensive 3 7        -- takes ~2 seconds, returns 1021
expensive 3 7        -- takes ~2 seconds again — a fresh call, unrelated to the last one

y = expensive 3 7    -- instant — y is just bound to the expression, not yet evaluated
y                     -- ~2 seconds — *now* it gets evaluated
y                     -- instant — the result is remembered; no need to redo the work
```

That "remember, don't redo" behavior — safe only because referentially transparent expressions always evaluate to the same result — also shows up inside function bodies, even when a variable is used more than once. Compare two functions that each seem to use `expensive 3 7` twice:

```haskell
f x = expensive 3 7 + x
f (expensive 3 7)    -- ~4 seconds — two *different* calls to expensive 3 7, each paid for separately

g x = x + x
g (expensive 3 7)    -- ~2 seconds — one call to expensive 3 7, bound to x, then reused twice
```

`f (expensive 3 7)` really does run `expensive 3 7` twice — once to build the argument, once inside `f`'s body — so it pays the full cost twice, about 4 seconds. `g (expensive 3 7)` looks like it should be just as slow, since `g`'s body also mentions its argument twice. But the argument is evaluated once, bound to `x`, and that single result gets reused — so it only costs about 2 seconds. Same mechanism as the `y` example above, just happening inside a function call instead of at the top level.

Laziness isn't just a curiosity — it's a real practical advantage:

- **No unnecessary computation** — the program only evaluates what's actually needed.
- **Fewer redundant computations** — referential transparency lets Haskell "remember" a result instead of recomputing it.
- **Evaluation can happen in any order, even in parallel** — with no side effects, independent expressions can't interfere with each other.
- **Large — even infinite — data structures become practical.** A program can construct just the part of a structure it needs, instead of the whole thing up front.

## Operators: Precedence and Associativity

!!! question "Think about it"
    How do you know that `5 - 1 - 2 * 2` means `(5 - 1) - (2 * 2)`, and not `((5 - 1) - 2) * 2` or `(5 - (1 - 2)) * 2`? All three are plausible ways to group the same symbols.

    ??? note "How Haskell resolves it"
        Two separate rules are doing the work. **Precedence** says `*` binds tighter than `-`, so `2 * 2` gets grouped first no matter what. **Associativity** says that when the *same* operator appears more than once — here, the two `-`s — ties are broken left to right (`-` is *left-associative*). Put together: group the multiplication first, then resolve the two subtractions left-to-right, giving `(5 - 1) - (2 * 2)`, which is `0`.

A little vocabulary to describe what just happened:

- **Operator** / **operand** — `+` is the operator in `1 + 2`; `1` and `2` are its operands.
- **Application** (or **apply**) — using an operator on its operands.
- **Ambiguous** / **disambiguate** — something with multiple possible readings; resolving it to one.
- **Precedence** — the rule for disambiguating *different* operators applied together.
- **Associativity** — the rule for disambiguating *repeated* applications of the *same* operator (left-associative resolves left-first; right-associative resolves right-first).

Some Haskell operators, highest precedence first:

| Operation | Operator(s) | Associativity |
|---|---|---|
| function application | *(juxtaposition, e.g. `f x`)* | left |
| exponentiation | `^`, `**` | right |
| multiplication, division | `*`, `/` | left |
| (in)equality | `==`, `/=`, `<`, `>`, `<=`, `>=` | left |
| logical and | `&&` | left |
| logical or | <code>&#124;&#124;</code> | left |

Function application sits at the very top — higher than any operator — which is why `show 4 ++ show 2` doesn't need parentheses around either `show` call.

## Operators Are Just Functions

Here's a fact that ties operators and functions together: **in Haskell, a binary operator is just a function that takes two arguments.** You can call one exactly like any other function — you just have to wrap a symbolic operator in parentheses first:

```haskell
(+) 1 2       -- 3
:t (&&)       -- (&&) :: Bool -> Bool -> Bool
```

And it works the other way too: any two-argument function can be used *as* an operator, using **infix notation** — surround the function name with backticks and put the arguments on either side:

```haskell
4 `div` 2      -- 2
17 `mod` 12    -- 5
```

Custom infix functions come with a catch, though. Suppose you define:

```haskell
addMod60 :: Integer -> Integer -> Integer
addMod60 x y = (x + y) `mod` 60
```

``50 `addMod60` 15`` works fine, giving `5`. But watch what happens in a slightly bigger expression:

```haskell
0 * 1 `addMod60` 2    -- 0 — not what you'd expect!
```

You'd want `0 * 1` to happen first, the same way it would if `addMod60` were an ordinary operator sharing `mod`'s precedence — leaving ``0 `addMod60` 2``, which is `2`. Instead Haskell gives `0`. The reason: a freshly defined infix function has no declared precedence, so Haskell falls back to treating it as an ordinary function call — and function calls have the *highest* precedence there is, higher than `*`. So this actually parses as ``0 * (1 `addMod60` 2)``: first ``1 `addMod60` 2`` evaluates to `3`, then `0 * 3` gives `0`.

A **fixity declaration** fixes this by telling Haskell exactly where your operator belongs in the precedence order, the same way built-in operators have one:

```haskell
infixl 7 `addMod60`

addMod60 :: Integer -> Integer -> Integer
addMod60 x y = (x + y) `mod` 60
```

`infixl 7` says `addMod60` is left-associative with precedence level 7 — the same precedence as `mod`. With this declaration in place, ``0 * 1 `addMod60` 2`` now parses the way you'd expect, and evaluates to `2`.

## Currying

Here's a claim that sounds wrong at first:

!!! question "Think about it"
    Every Haskell function takes exactly **one** argument. But you've already written `average x y = (x + y) / 2`, which sure looks like it takes two. What's going on?

The resolution starts with how you can read a function's type. `average :: Double -> Double -> Double` can be read two ways:

- "`average` takes two `Double`s and results in a `Double`," **or**
- "`average` takes a `Double` and results in a function, `Double -> Double`."

Both readings are correct, and they're the same fact — because `->` is right-associative, `Double -> Double -> Double` is really `Double -> (Double -> Double)`. Calling `average` with one argument doesn't fail; it hands you back a function still waiting for the second one.

It's worth seeing what actually happens when you try this, because the error Haskell gives is easy to misread:

```haskell
average 1.0
-- <interactive>: error:
--     • No instance for (Show (Double -> Double)) arising from a use of ‘print’
--     • In a stmt of an interactive GHCi command: print it
```

It's tempting to read this as "you didn't give `average` enough arguments" — but that's not the actual complaint. `average 1.0` succeeds; it evaluates just fine, to a value of type `Double -> Double`. The error only shows up because `ghci` then tries to *print* that value for you, and Haskell has no idea how to print a function. You can see the successful, unbroken function value directly by giving it a name instead of asking `ghci` to print it on the spot:

```haskell
temp = average 1.0    -- no error — temp is a Double -> Double function
:t temp                -- temp :: Double -> Double
temp 2.0               -- 1.5 — call the remaining function with the second argument
```

Watching a two-argument definition get rewritten step by step makes this concrete:

```haskell
increment :: Integer -> Integer
increment n = 1 + n
increment n = (+) 1 n      -- infix + is just the function (+)
increment n = ((+) 1) n    -- (+) applied to 1, then applied to n
increment n = (+ 1) n      -- drop the now-redundant parens
increment   = (+ 1)        -- both sides mention n applied last — drop it entirely
```

That last line — defining a function with no parameters mentioned at all — is called **point-free style**: the function is built entirely out of other functions, with no explicit parameter to point at.

A couple of terms for this:

- **Curried function** — a multi-argument function that actually takes its arguments one at a time. Every multi-argument Haskell function is curried.
- **Higher-order function** — a function whose input or output is itself a function. A language that supports this is said to have **first-class functions**.

(Small history aside, since names carry people: this technique is named after logician Haskell Curry — yes, that Haskell — even though Moses Schönfinkel described the same idea earlier. Naming credit doesn't always land on whoever got there first.)

## Function Composition

Once functions are values you can pass around, a natural next move is combining two functions into a new one. Given:

```haskell
increment :: Integer -> Integer
increment = (+ 1)

double :: Integer -> Integer
double = (* 2)

square :: Integer -> Integer
square = (^ 2)
```

**Function composition** takes two functions `g` and `f` and builds a new function `h` where `h(x) = g(f(x))` — run `f` first, then feed its result into `g`:

```haskell
compose :: (Integer -> Integer) -> (Integer -> Integer) -> Integer -> Integer
compose g f n = g (f n)
```

(More generally, if `f :: a -> b` and `g :: b -> c`, then `compose :: (b -> c) -> (a -> b) -> a -> c` — the types have to line up so that whatever `f` produces is exactly what `g` expects.)

Haskell has this operator built in, spelled `(.)`:

```haskell
(increment . double) 1    -- double 1 = 2, then increment 2 = 3
(double . increment) 1    -- increment 1 = 2, then double 2 = 4
(increment . square) 1    -- square 1 = 1, then increment 1 = 2
```

Order matters — `increment . double` and `double . increment` are different functions, because composition applies the right-hand function first. Small, single-purpose functions like `increment`, `double`, and `square` become genuinely reusable once you can snap them together like this.
