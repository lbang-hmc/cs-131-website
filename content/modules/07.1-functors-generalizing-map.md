## Remember `map`

```haskell
map (+1) [1, 2, 3]      -- [2,3,4]
map show [1, 2, 3]      -- ["1","2","3"]
```

The two calls transform their elements differently, but neither changes the list's structure. We still have three elements, in the same positions.

```haskell
map :: (a -> b) -> [a] -> [b]
```

Recall why `map` is so useful. We could write separate recursive functions to increment a list, double its elements, or convert them to strings. But all those functions would share the same traversal. `map` **factors out that repeated traversal**:

```haskell
myMap :: (a -> b) -> [a] -> [b]
myMap _ []     = []
myMap f (x:xs) = f x : myMap f xs
```

The function argument tells us **how to change the values**. The recursive definition determines **how to preserve the structure**.

## What About a Tree?

Let's use a binary tree that stores a value at each node:

```haskell
data Tree a
  = Empty
  | Node a (Tree a) (Tree a)
  deriving (Show, Eq)

exampleTree :: Tree Int
exampleTree =
  Node 5
    (Node 2 Empty Empty)
    (Node 7 (Node 1 Empty Empty) Empty)
```

Its shape is:

```text
       5
      / \
     2   7
        /
       1
```

We can write a function that transforms every value, while preserving every node and branch:

```haskell
mapTree :: (a -> b) -> Tree a -> Tree b
mapTree _ Empty = Empty
mapTree f (Node x left right) =
  Node (f x)
       (mapTree f left)
       (mapTree f right)
```

Try:

```haskell
mapTree (+10) exampleTree
```

The result has this shape:

```text
       15
      /  \
     12  17
        /
       11
```

Notice that our implementation is doing exactly what `map` did on lists: change the contents, but preserve the arrangement of the containers.

## The Common Pattern Has a Name

Compare the types:

```haskell
map     :: (a -> b) -> [a]    -> [b]
mapTree :: (a -> b) -> Tree a -> Tree b
```

The only difference is the *structure* we are mapping over. This suggests a general notion of a **mappable** structure.

Haskell calls such structures **functors** and provides a standard function named `fmap`:

```haskell
class Functor f where
  fmap :: (a -> b) -> f a -> f b
```

Here `f` does **not** mean the function we're applying. It stands for a **type constructor**: something like `[]`, `Tree`, or `Maybe`, which accepts an element type and makes a complete type.

For instance:

```text
Tree       is a type constructor
Tree Int   is a complete type
Tree Bool  is another complete type
```

That is why the `Functor` instance will be for `Tree`, rather than only for `Tree Int`. A mapping operation must be able to change the element type, such as from `Int` to `String`.

## Make `Tree` an Instance of `Functor`

We already know the implementation: it is `mapTree`, written using the standard typeclass interface.

```haskell
instance Functor Tree where
  fmap _ Empty = Empty
  fmap g (Node x left right) =
    Node (g x)
         (fmap g left)
         (fmap g right)
```

Now these all work:

```haskell
fmap (+10) exampleTree  -- Tree Int
fmap even exampleTree   -- Tree Bool
fmap show exampleTree   -- Tree String
```

The typeclass does not change how the tree is stored. It gives us a **common name** for an operation we've already discovered. This is another example of abstraction by recognizing and factoring out common structure.

## `Maybe` Is a Functor Too

Remember the essential definition:

```haskell
data Maybe a = Nothing | Just a
```

What would it mean to transform a value *inside* `Maybe` while preserving its structure?

```haskell
fmap (+1) (Just 5)   -- Just 6
fmap (+1) Nothing    -- Nothing
fmap show (Just 42)  -- Just "42"
```

A conceptual implementation is tiny:

```haskell
-- This instance already exists in Haskell; don't redefine it.
instance Functor Maybe where
  fmap _ Nothing  = Nothing
  fmap g (Just x) = Just (g x)
```

Here, “preserving the structure” means preserving the distinction between *a value is present* and *no value is present*. We do not have to pattern match every time we want to change a successful result.

## One More Example: `Either`

`Either e a` can represent a successful result (`Right a`) or an error (`Left e`). For this structure, `fmap` transforms the successful value and leaves an error alone:

```haskell
fmap (+1) (Right 5 :: Either String Int)
-- Right 6

fmap (+1) (Left "oops" :: Either String Int)
-- Left "oops"
```

We've now seen the same operation in several settings:

| Structure | What `fmap` preserves |
|---|---|
| List | Length and position of elements |
| Tree | Nodes and branching shape |
| `Maybe` | `Just` versus `Nothing` |
| `Either e` | `Right` versus `Left`, and any error value |

The kind of structure determines how mapping behaves.

---

## Two Simple Laws

A sensible `fmap` should obey two **functor laws**.

**Identity**

```haskell
fmap id = id
```

If you do not change any value, the whole structure should stay the same.

**Composition**

```haskell
fmap (g . h) = fmap g . fmap h
```

Changing the values first with `h` and then with `g` should be equivalent to changing them once with the combined function `g . h`.

For example, using a list:

```haskell
fmap (show . (+1)) [1, 2]
-- ["2","3"]

(fmap show . fmap (+1)) [1, 2]
-- ["2","3"]
```

These laws are more than style preferences: they express what we mean by a mapping operation that respects the structure.

## A Practical Note: Deriving `Functor`

For many suitable datatypes, GHC can generate this instance automatically:

```haskell
{-# LANGUAGE DeriveFunctor #-}

data Tree a
  = Empty
  | Node a (Tree a) (Tree a)
  deriving (Show, Eq, Functor)
```

This is convenient, but understanding the earlier hand-written instance explains *what* is being generated. (Use either the derived instance or the manual one, not both.)
