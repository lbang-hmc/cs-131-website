# Module 06.2: Practical Parsing with Parser Combinators

Module 06.1 gave us the conceptual picture:

```text
concrete syntax  --->  abstract syntax
                parser
```

and a grammar that describes valid source structure.

Now we need to actually write parsers.

We are going to use the course's provided Haskell parser-combinator library:

```haskell
import ParserCombinators
```

You do **not** need to understand how that library is implemented.

You need to understand how to **use** it.

The big idea is:

> Build complicated parsers by combining small parsers.

This should feel familiar.

Earlier in the course, higher-order functions let us build new computations by passing functions to functions.

A **parser combinator** does the same thing for parsers:

> A parser combinator takes one or more parsers and produces a new parser.

By the end of this module, you should be able to:

- read `Parser a` as "a parser that produces an `a`,"
- run small parsers with `parse`,
- use primitive parsers for characters, text, symbols, identifiers, and numbers,
- sequence parsers with `<+>`, `<-+>`, and `<+->`,
- choose between alternatives with `<|>`,
- transform successful parse results with `>>=:`,
- replace a successful parse result with a fixed value using `>>:`,
- filter results with `<=>`,
- repeat parsers with `many` and `some`,
- parse delimited and separated structures with `parens`, `braces`, and `sepBy`,
- translate simple grammar rules into parser-combinator expressions,
- construct AST nodes directly while parsing, and
- understand enough precedence and associativity to complete the piq parser assignment.

## A Parser Produces a Value

The key type is:

```haskell
Parser a
```

Read this as:

> a parser that, when successful, produces a value of type `a`.

Examples:

```haskell
Parser Char
```

produces a character.

```haskell
Parser String
```

produces a string.

```haskell
Parser Double
```

produces a `Double`.

```haskell
Parser Expr
```

produces an abstract syntax tree of type `Expr`.

That last one is our real destination.

### A useful mental model

Internally, a parser must keep track of things such as:

- whether parsing succeeded,
- what value was produced,
- what input remains,
- where an error occurred.

But you do not need the implementation details.

For this module, think:

```text
Parser a

input text
    |
    v
 parser
    |
    +---- failure
    |
    `---- value of type a
          + remaining input
```

Why does the parser need to keep track of remaining input?

Because we want to combine parsers.

If one parser consumes:

```text
move
```

from:

```text
move right 20
```

then the next parser should continue with:

```text
right 20
```

The library handles this state management for us.

## Running a Parser

Use:

```haskell
parse
```

to run a parser on an entire input string.

Conceptually:

```haskell
parse :: Parser a -> String -> a
```

For example:

```haskell
parse double "2.5"
```

produces:

```text
2.5
```

and:

```haskell
parse identifier "size2"
```

produces:

```text
"size2"
```

`parse` expects the parser to consume the whole input.

So this is fine:

```haskell
parse number "42"
```

but a parser that successfully consumes only the beginning of an input will still cause `parse` to complain that unexpected input remains.

That is useful for testing.

## Start Small: Primitive Parsers

The library already gives us parsers for common pieces of syntax.

### Single characters

```haskell
digit    :: Parser Char
letter   :: Parser Char
space    :: Parser Char
alphanum :: Parser Char
```

Examples:

```haskell
parse digit "7"
-- '7'
```

```haskell
parse letter "q"
-- 'q'
```

You can also ask for one particular character:

```haskell
char 'x'
```

or, more commonly when parsing source syntax with optional preceding whitespace:

```haskell
sym '('
sym ','
sym '+'
```

### Exact text

```haskell
text "move"
text "define"
text "pen-up"
```

recognizes exactly that sequence of characters.

For example:

```haskell
parse (text "hello") "   hello"
-- "hello"
```

Notice that `text` skips leading whitespace.

### Identifiers

```haskell
identifier :: Parser String
```

recognizes:

```text
letter followed by zero or more letters or digits
```

Examples:

```text
x
size
size2
box17
```

### Numbers

```haskell
number :: Parser Integer
double :: Parser Double
```

For piq, `double` is especially useful because expression literals become numeric AST values.

```haskell
parse double "-2.5"
-- -2.5
```

## Whitespace Is Mostly Handled for You

High-level library parsers such as:

```haskell
text
sym
identifier
number
double
```

skip preceding whitespace.

That means:

```haskell
parse (text "hello") "      hello"
```

works.

So does:

```haskell
parse (number <+> number) "3     4"
```

For piq, whitespace includes spaces, tabs, and newlines.

This matters because piq does **not** use newlines or semicolons as statement terminators.

These can mean the same thing:

```text
x = 10
square x
```

and:

```text
x = 10 square x
```

Do not build your parser around line boundaries.

Build it around the grammar.

## Parser Combinators

A parser by itself recognizes one thing.

A **parser combinator** lets us make a larger parser out of smaller ones.

The most important questions are:

```text
What should happen in sequence?
What are the alternatives?
What should repeat?
Which parsed results do I care about?
How do I turn those results into an AST?
```

The library gives us a small vocabulary for answering those questions directly.

---

## Sequencing: Parse This, Then That

Suppose we want:

```text
number number
```

We can sequence two number parsers with:

```haskell
number <+> number
```

Example:

```haskell
parse (number <+> number) "3 4"
```

produces:

```haskell
(3, 4)
```

So:

```haskell
p <+> q
```

means:

> parse `p`, then parse `q`, and keep both results as a pair.

Conceptually:

```text
p result = a
q result = b

p <+> q
result = (a, b)
```

### Sequencing several parsers

Be aware that:

```haskell
p <+> q <+> r
```

produces nested pairs:

```haskell
((pResult, qResult), rResult)
```

This looks slightly awkward at first, but we can later transform the result with a function.

## Sometimes Syntax Matters but Its Value Does Not

Suppose we want to parse:

```text
move 5
```

The word:

```text
move
```

must be present.

But the AST probably does not need to store the literal string `"move"`.

We care about the number `5`.

Use:

```haskell
p <-+> q
```

to:

> parse `p`, then parse `q`, but keep only `q`'s result.

Example:

```haskell
parse (text "move" <-+> number) "move 5"
```

produces:

```text
5
```

There is a symmetric version:

```haskell
p <+-> q
```

which keeps only `p`'s result.

These operators are extremely useful for punctuation and keywords.

For example:

```haskell
sym '(' <-+> expr <+-> sym ')'
```

means:

> require parentheses, but return only the expression inside them.

The library already packages that common pattern as:

```haskell
parens expr
```

## Choice: Parse This or That

A grammar often contains alternatives:

```text
factor ::= number | name | "(" expr ")"
```

The parser combinator:

```haskell
p <|> q
```

means:

> try parser `p`; if it fails, try parser `q`.

So a factor parser can conceptually look like:

```haskell
numberCase
  <|> variableCase
  <|> parenthesizedCase
```

This is one reason parser combinators are so convenient.

The Haskell structure can resemble the grammar structure.

```text
grammar:

factor ::= number
         | name
         | "(" expr ")"
```

```haskell
parser:

factor =
      numberCase
  <|> variableCase
  <|> parenthesizedCase
```

---

## Repetition: Zero or More, One or More

Grammars often contain repetition.

The library provides:

```haskell
many :: Parser a -> Parser [a]
some :: Parser a -> Parser [a]
```

Read:

```haskell
many p
```

as:

> parse `p` zero or more times.

Read:

```haskell
some p
```

as:

> parse `p` one or more times.

Example:

```haskell
parse (many digit) "123"
```

produces:

```haskell
"123"
```

because a Haskell `String` is a list of `Char`.

This makes grammar notation such as:

```text
statement*
```

very natural:

```haskell
many statement
```

A block containing zero or more statements then becomes conceptually:

```haskell
braces (many statement)
```

---

## Separated Lists

Procedure arguments and parameters are often comma-separated.

For example:

```text
1, 2, x + 3
```

The library gives us:

```haskell
sepBy p separator
```

which parses zero or more `p`s separated by `separator`.

Example:

```haskell
parse (sepBy number (sym ',')) "1, 2, 3"
```

produces:

```haskell
[1, 2, 3]
```

So if:

```haskell
expr :: Parser Expr
```

then:

```haskell
sepBy expr (sym ',')
```

has type:

```haskell
Parser [Expr]
```

and:

```haskell
parens (sepBy expr (sym ','))
```

is almost exactly what we need for procedure-call arguments.

## Transforming Results

So far, parsers have mostly returned whatever they recognized:

```haskell
double
```

returns a `Double`.

But we do not ultimately want:

```haskell
2.5
```

We want:

```haskell
Num 2.5
```

Suppose:

```haskell
Num :: Double -> Expr
```

The combinator:

```haskell
p >>=: f
```

means:

> run parser `p`, then apply function `f` to the parsed result.

So:

```haskell
double >>=: Num
```

has type:

```haskell
Parser Expr
```

It reads a `Double`, then wraps it in the AST constructor `Num`.

Example:

```text
input:
    2.5

double produces:
    2.5

Num transforms it into:
    Num 2.5
```

This is one of the most important moves in the whole assignment.

> A parser does not just recognize syntax. It can construct the corresponding AST as it goes.

### Constructors are functions

This should connect directly to Module 03.2.

If:

```haskell
Num :: Double -> Expr
```

then `Num` is just a function that turns a `Double` into an `Expr`.

So it can be passed directly to `>>=:`.

That is why:

```haskell
double >>=: Num
```

works so naturally.

---

## Returning a Fixed AST Value

Sometimes the concrete syntax itself completely determines the AST value.

Suppose:

```text
dot
```

corresponds to the AST constructor:

```haskell
Dot
```

We can parse the keyword and then ignore the string result.

The combinator:

```haskell
p >>: value
```

means:

> if `p` succeeds, ignore its result and return `value`.

So:

```haskell
identifier <=> (== "dot") >>: Dot
```

is a parser that:

1. requires the keyword `dot`,
2. returns the AST value `Dot`.

This is a compact example of the whole concrete-to-abstract transition:

```text
concrete syntax:  "dot"

        parser

abstract syntax:  Dot
```

---

## Filtering Results

Sometimes a parser recognizes a broad category, but we want only some of its results.

Use:

```haskell
p <=> predicate
```

to:

> run `p`, but succeed only if its result satisfies `predicate`.

For example:

```haskell
identifier <=> (\w -> length w > 3)
```

accepts an identifier only if it has more than three characters.

This is particularly useful for keywords and reserved names.

### Whole-word keywords

Suppose we want the keyword:

```text
dot
```

A tempting parser is:

```haskell
text "dot"
```

but that can recognize the prefix of:

```text
dotty
```

A better strategy is:

```haskell
identifier <=> (== "dot")
```

Now the parser first reads the **whole identifier**.

Then it checks whether that complete name is exactly `"dot"`.

### User-defined names

The same mechanism can exclude reserved words:

```haskell
identifier <=> (\w -> not (isReserved w))
```

This is the kind of parser we want for variable and procedure names.

## The Core Toolbox

For the piq assignment, the most useful pieces of the library can be summarized like this:

| Goal | Tool |
|---|---|
| parse a decimal number | `double` |
| parse an identifier | `identifier` |
| parse exact text | `text "..."` |
| parse one symbol | `sym 'c'` |
| parse `p`, then `q`, keep both | `p <+> q` |
| parse `p`, then `q`, keep `q` | `p <-+> q` |
| parse `p`, then `q`, keep `p` | `p <+-> q` |
| choose between parsers | `p <|> q` |
| transform a result | `p >>=: f` |
| replace a result with a fixed value | `p >>: v` |
| accept only results passing a test | `p <=> test` |
| zero or more | `many p` |
| one or more | `some p` |
| separator-separated list | `sepBy p sep` |
| parse inside parentheses | `parens p` |
| parse inside braces | `braces p` |

You do not need to memorize every combinator in the complete library.

You should become comfortable reading and combining this core set.

## Grammar Rules Become Parser Expressions

Now we can connect Module 06.1's grammar notation directly to Haskell.

### Example 1: a number expression

Suppose:

```haskell
data Expr
  = Num Double
  | Var String
  | ...
```

Grammar:

```text
factor ::= number
```

Parser:

```haskell
double >>=: Num
```

### Example 2: a variable

Grammar:

```text
factor ::= name
```

Parser:

```haskell
name >>=: Var
```

### Example 3: a parenthesized expression

Grammar:

```text
factor ::= "(" expr ")"
```

Parser:

```haskell
parens expr
```

Parentheses matter in the concrete syntax but do not need to survive in the AST.

### Put the alternatives together

Grammar:

```text
factor ::= number
         | name
         | "(" expr ")"
```

Parser shape:

```haskell
factor =
      (double >>=: Num)
  <|> (name   >>=: Var)
  <|> parens expr
```

That is exactly the relationship we want:

> The parser definition mirrors the grammar.

## A Statement Example

Suppose:

```text
square expr
```

should produce:

```haskell
Square expressionAST
```

We can read the concrete pieces as:

```haskell
identifier <=> (== "square") <-+> expr
```

which returns only the expression AST.

Then transform it:

```haskell
identifier <=> (== "square") <-+> expr >>=: Square
```

Read this from left to right:

```text
recognize "square"
then parse an expression
then wrap that expression in Square
```

The result is a:

```haskell
Parser Stmt
```

For input:

```text
square 12
```

we get something like:

```haskell
Square (Num 12)
```

This is the basic pattern you will repeat throughout the assignment.

## A Procedure Call Example

Consider:

```text
box(20, 5)
```

Suppose the AST constructor is:

```haskell
Call :: String -> [Expr] -> Stmt
```

The grammar is conceptually:

```text
call ::= name "(" arguments ")"

arguments ::= expr ("," expr)*
            | empty
```

The useful parser pieces are:

```haskell
name
```

and:

```haskell
parens (sepBy expr (sym ','))
```

Sequencing them:

```haskell
name <+> parens (sepBy expr (sym ','))
```

produces a pair:

```haskell
(nameResult, argumentResults)
```

Then:

```haskell
>>=: uncurry Call
```

can turn that pair into:

```haskell
Call nameResult argumentResults
```

The resulting pattern is:

```haskell
name
  <+> parens (sepBy expr (sym ','))
  >>=: uncurry Call
```

You do not need to memorize this exact line.

You should understand how it was derived from the grammar.

## A Block Example

Suppose:

```text
block ::= "{" statement* "}"
```

Then:

```haskell
many stmt
```

parses zero or more statements.

And:

```haskell
braces (many stmt)
```

parses them inside braces.

So:

```text
{ dot square 3 }
```

might produce:

```haskell
[Dot, Square (Num 3)]
```

while:

```text
{}
```

produces:

```haskell
[]
```

Notice again that braces are concrete syntax.

The AST only needs the list of statements.

## Precedence and Associativity

The assignment's expression grammar is:

```text
expr   ::= term   (("+" | "-") term)*
term   ::= factor (("*" | "/") factor)*
factor ::= number | name | "(" expr ")"
```

There are two things to understand.

### Precedence comes from grammar levels

Because `term` handles multiplication and division before the surrounding `expr` combines terms with addition or subtraction:

```text
x + 5 * 2
```

becomes:

```haskell
Add
  (Var "x")
  (Mul (Num 5) (Num 2))
```

### Associativity comes from how repeated pieces are combined

For:

```text
10 - 3 - 2
```

we want:

```haskell
Sub
  (Sub (Num 10) (Num 3))
  (Num 2)
```

which means:

```text
(10 - 3) - 2
```

The assignment gives you a small helper pattern for combining a first operand with a list of subsequent operator/operand pairs from the left.

You do not need a broader theory of parsing algorithms here.

You need to be able to look at:

```text
first operand: Num 10

remaining pieces:
[(Sub, Num 3), (Sub, Num 2)]
```

and see why left-to-right combination produces the desired AST.

## Reading More Complicated Parser Expressions

As parsers get larger, two practical details matter.

### Sequencing produces nested pairs

```haskell
a <+> b <+> c
```

produces:

```haskell
((aResult, bResult), cResult)
```

So a transformation might use a pattern:

```haskell
>>=: \((aResult, bResult), cResult) -> ...
```

For a two-result pair, the ordinary Haskell helper:

```haskell
uncurry
```

is often useful.

If:

```haskell
f :: a -> b -> c
```

then:

```haskell
uncurry f :: (a, b) -> c
```

which is exactly what we often need after `<+>`.

### Parenthesize alternatives when transforming them

The assignment library's operators have precedence rules of their own.

When you combine transformed alternatives, prefer to write:

```haskell
(p1 >>=: f) <|> (p2 >>=: g)
```

rather than relying on yourself to remember how all the parser operators group.

Clear parentheses are cheap.

Debugging an accidentally grouped parser is not.

## The Whole piq Pipeline

The parser assignment completes a pipeline you have already built most of:

```text
piq source file
      |
      v
    parser
      |
      v
     AST
      |
      v
   compiler
      |
      v
    Python
      |
      v
 preview / plotter
```

For example:

```text
square 20
```

becomes:

```haskell
Square (Num 20)
```

which the compiler can then translate into plotter commands.

The parser does not need to know how `Square` is eventually drawn.

The compiler does not need to know whether the programmer wrote:

```text
square 20
```

or some other concrete syntax that happened to produce the same AST.

The AST is the boundary between those concerns.

That separation is one of the recurring ideas of the course.

## How to Approach the Assignment

When you reach a parser TODO, avoid staring at the whole language.

Instead:

1. Find the corresponding grammar rule.
2. Identify the smaller parsers you already have.
3. Ask whether the rule requires:
   - sequence,
   - choice,
   - repetition,
   - separators,
   - delimiters,
   - filtering.
4. Decide which concrete-syntax results should be discarded.
5. Decide which results are needed to build the AST.
6. Combine the parsers.
7. Transform the result into the appropriate AST constructor.
8. Test the smallest piece before moving on.

For example:

```text
forLoop
```

looks complicated as a whole.

But structurally it is just:

```text
"for"
name
"from"
expr
"to"
expr
block
```

That is a sequence of smaller parsers whose interesting results are:

```text
name
from-expression
to-expression
block
```

Those four values are exactly what the `For` AST constructor needs.

This is the mindset to carry into every part of the assignment.

## Put the Ideas Together

The central idea of this module is:

> **Parsers are values that can be combined.**

The main correspondence is:

```text
grammar idea                 parser-combinator idea
------------                 ----------------------

A then B                     sequencing
A or B                       <|>
zero or more A               many
one or more A                some
A separated by commas        sepBy
A inside (...)               parens
A inside {...}               braces
recognize then transform     >>=:
recognize fixed syntax       >>:
recognize then filter        <=>
```

And the most important transformation is:

```text
concrete syntax
      |
      v
parser combinators
      |
      v
AST constructors
```

Once you can read a grammar rule and identify those pieces, the assignment becomes a sequence of small composition problems rather than one giant "write a parser" problem.
