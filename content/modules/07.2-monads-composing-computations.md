# Module 07.2: Monads — Composing Computations

In Module 07.1, we discovered that `fmap` generalizes the idea of `map`: given a function `a -> b`, we can transform values *inside* a list, tree, `Maybe`, or another functor.

Now consider functions that return a `Maybe` **themselves**. How do we compose those functions without repeatedly writing code to check for `Nothing`?

That small problem will lead us to a surprisingly general abstraction: **monads**.

By the end of this module, you should be able to:

- explain why ordinary composition fails for `Maybe`-producing functions,
- derive and use `(>>=)` (pronounced *bind*),
- understand `pure`,
- read a small `Monad` instance,
- use `do` notation, and
- describe how the same interface supports different kinds of computations.

## Ordinary Function Composition

Recall function composition (`.`) from Module 02.2. Take two ordinary functions:

```haskell
double :: Double -> Double
double x = 2 * x

increment :: Double -> Double
increment x = x + 1
```

We can compose them:

```haskell
(increment . double) 5  -- 11.0
```

Composition works because the first function returns the kind of value the second function expects:

```haskell
f :: a -> b
g :: b -> c

-- g . f :: a -> c
```

But some useful functions don't return an ordinary value directly.

---

## A Square Root That Might Fail

Recall that `Maybe` distinguishes a present value from a missing one. Let's make a function that declines to compute real square roots of negative numbers:

```haskell
safeSqrt :: Double -> Maybe Double
safeSqrt x =
  if x < 0
    then Nothing
    else Just (sqrt x)
```

Examples:

```haskell
safeSqrt 9      -- Just 3.0
safeSqrt (-4)   -- Nothing
```

Now suppose we want a **safe fourth root**. Mathematically, we can take the square root twice. It is tempting to write:

```haskell
safeFourthRoot = safeSqrt . safeSqrt  -- TYPE ERROR
```

The types don't fit:

```text
safeSqrt :: Double -> Maybe Double

first result:       Maybe Double
second input needs: Double
```

The second `safeSqrt` expects a `Double`, not a `Maybe Double`.

## A Working Solution, with Repeated Bookkeeping

We already know how to solve the problem with pattern matching:

```haskell
safeFourthRoot :: Double -> Maybe Double
safeFourthRoot x =
  case safeSqrt x of
    Nothing -> Nothing
    Just y  -> safeSqrt y
```

This handles both possibilities. If the first square root fails, the whole calculation fails. Otherwise, we feed the value to the next square root.

What about an eighth root?

```haskell
safeEighthRoot :: Double -> Maybe Double
safeEighthRoot x =
  case safeFourthRoot x of
    Nothing -> Nothing
    Just y  -> safeSqrt y
```

We're repeating a pattern:

```haskell
case someResult of
  Nothing -> Nothing
  Just x  -> nextStep x
```

Most of this code has nothing to do with square roots. It is the same *failure-handling plumbing* every time. That suggests a familiar course theme: **factor out what repeats**.

---

## Extract a Reusable Operation

Let's give that pattern a name:

```haskell
andThen :: Maybe a -> (a -> Maybe b) -> Maybe b
andThen Nothing  _ = Nothing
andThen (Just x) f = f x
```

Read the type slowly:

```text
Maybe a          ->   (a -> Maybe b)    -> Maybe b
previous result       next computation    final result
```

If the previous result is `Nothing`, we stop. If it is `Just x`, we give `x` to the next function. Notice that this next function can *also fail*.

Now the earlier definitions become:

```haskell
safeFourthRoot x = safeSqrt x `andThen` safeSqrt

safeEighthRoot x =
  safeSqrt x
    `andThen` safeSqrt
    `andThen` safeSqrt
```

The checks are gone from the main program: they live in `andThen`.

This operation is so useful that Haskell has a standard name for it:

```haskell
(>>=) :: Monad m => m a -> (a -> m b) -> m b
```

It is called **bind**. `Maybe` already implements it, with the behavior we just defined as `andThen`.

```haskell
safeFourthRoot x = safeSqrt x >>= safeSqrt
```

The key idea is not the strange-looking operator. It is the repeated structure that the operator eliminates.

## Composing Different Possibly Failing Operations

This is not just a special trick for repeated square roots. Consider another operation that might fail:

```haskell
safeReciprocal :: Double -> Maybe Double
safeReciprocal 0 = Nothing
safeReciprocal x = Just (1 / x)
```

We can combine it with square root:

```haskell
safeSqrt 4 >>= safeReciprocal
-- Just 0.5

safeSqrt (-4) >>= safeReciprocal
-- Nothing
```

The two functions have different jobs, but the same result structure. Bind takes care of propagating failure consistently.

Notice the distinction from Module 07.1:

```haskell
fmap (+1) (Just 5)
-- Just 6

Just 5 >>= safeReciprocal
-- Just 0.2
```

**`fmap`** expects a function of type `a -> b`, returning an *ordinary value*.

**`>>=`** expects a function of type `a -> m b`, returning another value wrapped in a *context*.

Here **context** just means the wrapper around a value. For `Maybe`, the context is whether a value is present at all (`Just`) or missing (`Nothing`). The rest of this module uses the word in that sense.

If we mistakenly tried:

```haskell
fmap safeSqrt (Just 16)
```

we would get:

```haskell
Just (Just 4.0)
```

A nested `Maybe`! Bind knows how to sequence the computation without accumulating an extra layer of `Maybe`.

## Putting an Ordinary Value into a Context: `pure`

We also need a simple way to produce an ordinary successful result inside a context:

```haskell
pure 5 :: Maybe Int
-- Just 5
```

The general type is:

```haskell
pure :: Applicative m => a -> m a
```

(`Applicative` is another typeclass; the next section says just enough about it.)

For `Maybe`, `pure` behaves like `Just`. It **does not check** that a calculation is safe. It only places an already-computed value into the chosen context.

So the two play different roles: a safe operation such as `safeReciprocal` can *introduce* a failure; `pure` never does. It always succeeds.

Older Haskell materials commonly use `return` for this operation. Despite the name, Haskell's `return` is **not** the `return` statement from Python or Java: it doesn't exit a function, it just wraps a value, exactly like `pure`. In modern Haskell, **we will use `pure`**.

---

## The Absolute Minimum About Applicatives

We have seen `Functor`, which provides `fmap`. Modern Haskell places another typeclass between `Functor` and `Monad`:

```haskell
class Functor f => Applicative f where
  pure  :: a -> f a
  (<*>) :: f (a -> b) -> f a -> f b
```

The idea of `<*>` is to apply a function *inside a context* to an argument *inside a context*:

```haskell
Just (+1) <*> Just 5  -- Just 6
Just (+1) <*> Nothing -- Nothing
```

For our purposes, the takeaway is small: `Applicative` is where `pure` is defined, and (as the next section shows) every `Monad` is also an `Applicative`. We won't go further into applicatives in this course.

## The `Monad` Typeclass and a Concrete Instance

Here's the relevant portion of the modern class definition:

```haskell
class Applicative m => Monad m where
  (>>=) :: m a -> (a -> m b) -> m b
```

The relationship is:

```text
Functor        Applicative          Monad
  fmap    --->   pure, <*>    --->     >>=
```

The `Applicative m =>` in the class header is a **superclass** constraint, like `Eq a => Ord a` in Module 07.1. Every `Monad` must also be an `Applicative`, and (from `Functor f => Applicative f` in the previous section) every `Applicative` must also be a `Functor`.

To see that these are just ordinary Haskell functions, look at *illustrative* definitions for `Maybe`. **They already exist in the standard library; don't paste these instance declarations into your code.**

```haskell
instance Functor Maybe where
  fmap _ Nothing  = Nothing
  fmap f (Just x) = Just (f x)

instance Applicative Maybe where
  pure = Just
  Nothing <*> _ = Nothing
  Just f  <*> x = fmap f x

instance Monad Maybe where
  Nothing >>= _ = Nothing
  Just x  >>= f = f x
```

The `Monad` part is exactly our earlier `andThen` pattern. Nothing supernatural happened: we found a useful repetitive operation and gave it a shared interface.

## `do` Notation: Easier to Read, Same Meaning

Long chains of binds can become hard to read:

```haskell
example :: Double -> Maybe Double
example x =
  safeSqrt x >>= \a ->
  safeReciprocal a >>= \b ->
  pure (a + b)
```

Haskell's **`do` notation** is a more readable way to write the same sequence:

```haskell
example :: Double -> Maybe Double
example x = do
  a <- safeSqrt x
  b <- safeReciprocal a
  pure (a + b)
```

The translation to remember is:

```haskell
do
  a <- first
  b <- second a
  finish a b
```

means (roughly):

```haskell
first >>= \a ->
second a >>= \b ->
finish a b
```

For `Maybe`, the rest of the block is skipped if any preceding step produces `Nothing`. The `do` block itself does not perform the check; the **`Maybe` instance of bind** does.

### Three practical rules

**1. Use `<-` for computations in the context.** If `safeSqrt x :: Maybe Double`, then:

```haskell
a <- safeSqrt x
```

binds `a :: Double` within the remainder of the `do` block when the computation succeeds. This is **not mutable assignment**.

**2. Use `let` for ordinary values.** For example:

```haskell
let doubled = 2 * a
```

There is no `in` in this `do`-block `let` statement. This would *not* be appropriate:

```haskell
doubled <- 2 * a   -- WRONG: right side is not a Maybe computation
```

**3. The final line determines the result of the `do` block.** For instance:

```haskell
pure doubled
```

produces a `Maybe Double`. A final line that is just `doubled` would have type `Double`, not `Maybe Double`.

You may also see a line that's a computation by itself, with no `<-`. Its result is ignored, but the computation is still sequenced. We won't need to dwell on that form now.

## Other Meanings of Sequencing

`Maybe` is a monad whose sequencing means **continue on success, stop on failure**. But the same interface works elsewhere.

**Lists:** A computation can have *multiple results*. Bind applies the function to each value and concatenates the resulting lists:

```haskell
[1, 2] >>= \x -> [x, x * 10]
-- [1,10,2,20]
```

**`IO`:** A computation can perform input/output operations, which we can sequence with `do`:

```haskell
main :: IO ()
main = do
  name <- getLine
  putStrLn ("Hello, " ++ name)
```

Here `getLine :: IO String` is a computation that reads a line of input and produces a `String`, and `putStrLn :: String -> IO ()` prints a line. (`()` is Haskell's "no interesting result" type.) This is how a standalone Haskell program does input and output. So far in this course you've only run code through `ghci` and test suites, so you haven't needed it.

**Parsers:** The course's `Parser` type from Module 06.2 is also a monad (see the [ParserBase Reference](../how-to/parser-base.md)). But be careful with a look-alike operator: the `>>=:` you used in 06.2 is **not** bind. Specialized to parsers, it behaves like this:

```haskell
(>>=:) :: Parser a -> (a -> b) -> Parser b
p >>=: f = fmap f p
```

It transforms a parser's result with an *ordinary* function `a -> b`, so it's really `fmap` from Module 07.1 with its arguments flipped. Real bind, `>>=`, takes a function `a -> Parser b`, which would let the *next parser* depend on what was just parsed. We didn't need that in 06.2.

Different monads give **different meanings to sequencing**. `do` notation does not itself skip steps, produce multiple results, or perform I/O; the type and its `>>=` determine the behavior.

## Three Short Laws

Just as functors obey laws, monads obey laws describing sensible sequencing. Here `m` means an existing monadic computation, and `f` and `g` are functions that produce monadic computations.

**Left identity:**

```haskell
pure x >>= f   =   f x
```

Wrapping an ordinary value before immediately using it changes nothing.

**Right identity:**

```haskell
m >>= pure   =   m
```

Taking a result and wrapping it straight back up changes nothing.

**Associativity:**

```haskell
(m >>= f) >>= g   =   m >>= (\x -> f x >>= g)
```

Grouping a sequence differently doesn't change its meaning. Importantly, **this does not mean that we can reorder the steps**.

These are laws of *behavioral equivalence*, not necessarily executable Haskell `==` tests; not every monadic type supports `Eq`.

## Where Homework 7 Goes Next

We've learned to remove repetitive failure checks from programs that use `Maybe`. But failure isn't the only kind of bookkeeping.

Suppose you have a tiny arithmetic-language evaluator:

```haskell
data Term = Num Int | Div Term Term

eval :: Term -> Int
```

What if you later want it to report errors, count evaluation steps, or produce a trace? A naive solution can bury the actual evaluation algorithm under error checks, a step counter passed through every recursive call, or string concatenation for the trace.

In Homework 7, you'll build these variations and discover how the same sequencing abstraction can keep the core evaluator understandable.

The recurring idea of this course is once again **abstraction through factoring out repetition**. Monads provide a standard interface for abstracting the plumbing around a sequence of computations.
