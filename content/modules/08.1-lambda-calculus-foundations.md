# Module 08.1: Lambda Calculus — Computation with Nothing but Functions

In earlier modules, we learned to write programs using functions, to represent programs as data, and to give those programs meaning by evaluating them.

Now we're going to examine a very small language that gets rid of almost everything we normally expect from a programming language.

No numbers. No Booleans. No lists. No built-in conditionals. No named function definitions. No loops.

There are just **variables, function definitions, and function applications**.

This language is called the **untyped lambda calculus** (λ-calculus). Despite its simplicity, it is powerful enough to express general computation. We'll learn its rules in this module, then use them to construct familiar programming concepts in Modules 08.2 and 08.3.

**By the end of this module, you should be able to** read and write lambda expressions; identify a function's parameter, body, bound variables, and free variables; perform simple **β-reductions**; explain why **α-renaming** matters; distinguish reduction from normal form; and use the `lc` interpreter on the CS 131 server to experiment.

## Why Invent a Language This Small?

In the 1930s, mathematicians were trying to make the informal idea of *effective computation* precise. What, exactly, does it mean for something to be computable by following a mechanical procedure?

**Alan Turing** approached this question with machines that manipulate symbols according to explicit rules. **Alonzo Church** approached it using functions and symbolic substitution. His system became the lambda calculus.

These approaches look very different. One emphasizes changes to the state of a machine; the other emphasizes function application. Yet they characterize the same broad class of computable functions. This is one reason both are central to the foundations of computer science.

Lambda calculus also connects directly to our course:

- In Haskell, we've treated **functions as values** that can be passed around, returned, and applied.
- When building interpreters, we've used **substitution, environments, and scope** to explain what programs mean.
- When studying abstraction, we've asked how much machinery is really necessary to express an idea.

Lambda calculus takes that last question to an extreme: **how much computation can we express if functions are almost all we have?**

## The Entire Language

Here is the grammar of our small language:

```text
expr ::= variable
       | (expr expr)
       | (λ variable . expr)
```

For now, assume variables are single lowercase letters such as `x`, `y`, and `z`. We will write expressions with all their parentheses so the structure is completely clear.

There are only **three** kinds of expressions.

### A variable

```text
x
```

This is a complete, valid lambda expression. So are `y` and `z`.

A variable is just a symbol. Unlike a number, it doesn't inherently represent a particular value. Its meaning depends on whether some enclosing lambda abstraction binds it.

### A function application

```text
(f x)
```

This means: **apply `f` to `x`**.

The left expression is the function; the right expression is the argument.

Importantly, *both* parts can be arbitrary lambda expressions, not just letters:

```text
((λx.x) y)
```

The function is `(λx.x)` and the argument is `y`.

### A lambda abstraction

```text
(λx.x)
```

This represents an anonymous function: a function with parameter `x` and body `x`.

Its Haskell equivalent is:

```haskell
\x -> x
```

Another example:

```text
(λx.y)
```

This is a function that ignores its parameter `x` and has the body `y`.

Note that lambda calculus has **no built-in Haskell values or operations**. For now, expressions such as `x + 1`, `True`, or `[1,2]` are *not* pure lambda-calculus expressions. We'll learn how to represent things like these using functions.

### Parentheses are structure

In our fully parenthesized notation, applications are binary:

```text
((f x) y)
```

means "apply `f` to `x`, then apply the result to `y`."

Compare:

```text
(f (x y))
```

which means "apply `x` to `y` first, then pass that result to `f`."

Those can behave very differently!

You may encounter the convenient abbreviation:

```text
f x y
```

which usually means `((f x) y)`. When learning the rules, we will prefer the explicit version.

Similarly, some writing omits outer parentheses or writes `λx.λy.x` instead of `(λx.(λy.x))`. These abbreviations are helpful after the underlying structure is clear.

## Functions, Parameters, and Scope

Let's examine:

```text
(λx.(x y))
```

We can identify:

```text
 λ x . (x y)
   ^     ^ ^
   |     | |
parameter | free variable y
          |
    occurrence of x
```

The lambda binds occurrences of `x` in its body.

This should sound familiar: we discussed **scope** when building interpreters with environments and closures.

### Bound variables

Consider:

```text
(λx.(x x))
```

Both occurrences of `x` in the body are **bound** by the `λx` at the beginning.

The body can use the parameter more than once, just as a Haskell function can.

### Free variables

Now consider:

```text
(λx.(x y))
```

The occurrence of `x` in the body is bound by `λx`, but **`y` is free**. There is no enclosing `λy` that binds it.

A free variable is not necessarily an error. We can work with open expressions whose meaning depends on something outside the expression.

### Nested scopes

Consider:

```text
(λx.(λy.(x y)))
```

The inner body `(x y)` uses **both** parameters:

- `x` is bound by the *outer* lambda.
- `y` is bound by the *inner* lambda.

Now consider:

```text
(λx.(λx.x))
```

Here the occurrence of `x` in the innermost body is bound by the **inner** `λx`. It shadows the outer binder.

**Important:** "Bound" and "free" describe *occurrences* of variables, not just their spellings. The same letter can be bound in one place and free in another.

## Computation by β-Reduction

In an ordinary programming language, applying a function means supplying an argument and evaluating the function body.

Lambda calculus formalizes that basic idea with **β-reduction** (pronounced "beta reduction").

Start with the identity function:

```text
(λx.x)
```

Apply it to `y`:

```text
((λx.x) y)
```

To evaluate the application:

1. Find the parameter (`x`).
2. Find the function body (`x`).
3. Replace the free occurrences of `x` *in the body* with the argument (`y`).

The result is:

```text
((λx.x) y)  →β  y
```

This is one β-reduction step.

### A more interesting body

Consider:

```text
((λx.(x z)) y)
```

We substitute `y` for `x` in the body `(x z)`:

```text
(x z)       -- original body
(y z)       -- after substitution
```

Therefore:

```text
((λx.(x z)) y)  →β  (y z)
```

Notice that we do **not** replace `z`. Only the occurrences bound by the parameter being applied are replaced.

### A function that ignores its argument

```text
((λx.z) y)  →β  z
```

The body contains no occurrence of the parameter `x`, so substitution changes nothing.

The argument is simply not used.

### Functions returning functions

Consider:

```text
((λx.(λy.x)) a)
```

The outer function takes an argument and returns another function:

```text
((λx.(λy.x)) a)  →β  (λy.a)
```

The resulting function remembers `a` in its body and ignores whatever argument is later passed for `y`.

This is the lambda-calculus version of a familiar Haskell idea: **currying and partial application**.

For example, the Haskell function:

```haskell
\x -> \y -> x
```

returns a function after receiving its first argument.

### A two-step computation

Now apply two arguments:

```text
(((λx.(λy.x)) a) b)
```

First apply the outer lambda:

```text
(((λx.(λy.x)) a) b)
             →β
((λy.a) b)
             →β
a
```

One argument at a time, exactly as with curried Haskell functions.

!!! note "β-reduction versus evaluating arithmetic"
    Our reduction steps manipulate **expressions**, not machine integers. The symbols `a`, `b`, and `z` are variables, not secretly numbers. Lambda calculus will only acquire something like numeric computation once we build an encoding for numbers.

## α-Equivalence: Names Aren't the Important Part

These are the same function, except that we chose different names for its parameter:

```text
(λx.x)
(λw.w)
```

We say that they are **α-equivalent** ("alpha equivalent").

In Haskell, it's the same idea as:

```haskell
\x -> x
```

and:

```haskell
\w -> w
```

Changing a bound variable's name does not change the function's behavior, as long as we rename **exactly the occurrences it binds** and do not accidentally change which binder an occurrence belongs to.

For instance:

```text
(λx.(x z))
```

is α-equivalent to:

```text
(λw.(w z))
```

But it is **not** α-equivalent to:

```text
(λw.(w w))
```

because that second expression changes the free `z` into a bound variable.

### Why renaming can matter during substitution

Suppose we try to reduce:

```text
((λx.(λy.x)) y)
```

A naive text replacement would turn the body `(λy.x)` into:

```text
(λy.y)
```

But that would be wrong!

Before substitution, the argument `y` is a **free** variable. In the naive result, it has become bound by `λy`. This is called **variable capture**.

To avoid it, first rename the inner bound variable `y` to a fresh name, say `z`:

```text
((λx.(λy.x)) y)
```

is α-equivalent to:

```text
((λx.(λz.x)) y)
```

Now substitute:

```text
((λx.(λz.x)) y)  →β  (λz.y)
```

Here the `y` remains free, exactly as it should.

When you try this in `lc` later in this module, you'll see it do the same renaming automatically: it picks the fresh name `y'` and prints `(λy'.y)`.

This is **capture-avoiding substitution**: when reducing an application, we preserve which variable occurrences are free and which are bound.

## Reduction Order, Normal Forms, and Nontermination

A lambda expression can sometimes contain **more than one** place where β-reduction is possible.

A subexpression of the form:

```text
((λx.body) argument)
```

is called a **redex** (short for *reducible expression*).

A **normal form** is an expression with **no β-redexes left**.

For example, `y` is in normal form. So is `(λx.x)`. Neither contains an application of a lambda abstraction to an argument.

### Some computations never finish

Consider:

```text
Ω = ((λx.(x x)) (λx.(x x)))
```

The name `Ω` is just a convenient abbreviation.

What happens if we reduce it?

The function body is `(x x)`. Substitute the argument `(λx.(x x))` for both occurrences of `x`:

```text
((λx.(x x)) (λx.(x x)))
         →β
((λx.(x x)) (λx.(x x)))
```

We are back where we started. The same step can repeat forever.

So not every lambda expression has a normal form.

### Does reduction order matter?

Consider:

```text
((λx.z) Ω)
```

The outer function ignores its argument. If we reduce that outer application first, we get `z` immediately.

If we insist on reducing `Ω` first, we can get stuck reducing forever.

This echoes something we learned about **lazy evaluation in Haskell**: evaluating an unused argument may be unnecessary, and in some cases doing so would prevent termination.

We won't develop a complete theory of reduction strategies here. The important ideas are that **a β-reduction is a precise local rule**, and that **different choices about what to reduce next can affect whether we reach a result**.

The interpreter accepts a backslash in place of the Greek lambda character:


## What to Carry Forward

The lambda calculus is built entirely from:

```text
variable
application
abstraction
```

The key operation is **β-reduction**: apply a function by substituting an argument for its parameter in the body, while respecting scope.

Three ideas make that rule precise:

- **Free and bound occurrences:** the same name can refer to different things in different scopes.
- **α-equivalence:** bound-variable names can change without changing the meaning.
- **Capture avoidance:** substitution must not accidentally change which variables are bound.

Some expressions reduce to normal forms; others reduce forever.

In the next module, we'll confront an apparent problem: if our entire language consists of functions, where do Booleans, numbers, pairs, and lists come from?

Rather than adding new primitive constructs, we'll **encode them as functions**.
