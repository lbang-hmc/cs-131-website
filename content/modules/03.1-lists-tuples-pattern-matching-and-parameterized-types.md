# Module 03.1: Lists, Tuples, Pattern Matching, and Parameterized Types

So far, we have mostly computed with individual values: numbers, Booleans, strings, and functions. Now we will start working seriously with **structured data**.

This module focuses on four ideas that fit together especially well in Haskell:

- **lists**, for collecting any number of values of the same type,
- **functions on lists**, especially recursive functions, `map`, and `filter`,
- **pattern matching**, for taking structured values apart according to their shape,
- **tuples**, for grouping a fixed number of values that may have different types, and
- **parameterized types**, which let us describe general patterns like "a list of *some* type."

There is a practical reason to learn all of this: lists are everywhere in Haskell. There is also a deeper reason. Lists are recursive data structures, and functional programming makes heavy use of recursion. Add pattern matching and higher-order functions, and we get a compact way to express computations that would often be written as loops and mutable accumulators in an imperative language.

- pattern-match on lists using `case` expressions and function definitions,
- recognize empty-list and nonempty-list cases as the natural structure of recursive list functions,
- construct and pattern-match on tuples,
- read type variables such as `a` and `b` in list-function types, and
- explain what it means for a type such as `[a]` to be parameterized.

## Why Lists?

There are at least two good reasons for us to care about lists.

### The practical reason: put related data together

Imagine storing three related values separately:

```haskell
firstVal  = 5
secondVal = 3
thirdVal  = 19
```

Usually it is much more useful to collect them:

```haskell
vals = [5, 3, 19]
```

Other languages give you analogous structures: arrays, linked lists, vectors, Python lists, and so on. The details differ, but the motivation is familiar.

Side by side, the contrast is the whole point:

```text
first_val  = 5            vals = [5, 3, 19]
second_val = 3
third_val  = 19
```

Three names to declare, track, and pass around separately become one name that carries all three values together.

### The pedagogical reason: lists are recursive

More importantly for this course, lists have a beautifully recursive structure.

A list is either:

1. **empty**, or
2. **an element followed by another list**.

That second clause defines a list in terms of another list. This is a recursive definition.

In Haskell notation, we can say:

> A list is either `[]`, or it has the form `x : xs`.

Here:

- `[]` is the empty list,
- `x` is one element, and
- `xs` is another list containing everything after that first element.

This is going to matter enormously because a recursive data structure naturally suggests recursive programs.

For example, a recursive function over a list often has exactly the same two cases:

1. What should happen for `[]`?
2. If the list has the form `x : xs`, what should happen to `x`, and how should we recurse on `xs`?

That is the basic pattern we will use again and again.

## Lists in Haskell

### Basic list syntax

Haskell lists use square brackets, with elements separated by commas:

```haskell
[4, 9, -13, 5, 1]
[False, True, False, False]
[3.1, 3.14, 3.141, 3.1419]
[]
[[1,2,3], [4,5,6,7], [8,9]]
```

The last example is a list whose elements are themselves lists.

### Lists are homogeneous

Every element of a Haskell list must have the same type.

For example:

```haskell
[True, False, True]
```

is fine because every element has type `Bool`.

But:

```haskell
[15, True]
```

does not type-check. One element is numeric and the other is Boolean.

<br>*Haskell cannot pick one element type that fits both `15` and `True`, so `[15, True]` does not type-check.*

### Strings are lists too

A Haskell `String` is a list of characters.

So:

```haskell
"hello"
```

is another notation for:

```haskell
['h', 'e', 'l', 'l', 'o']
```

and its type can be written either as:

```haskell
String
```

or equivalently:

```haskell
[Char]
```

This explains why ordinary list operations often work on strings.

## Building Lists with `:`

The **cons operator**, written `:`, attaches one element to the front of a list.

```haskell
3 : [7, 15, 4]
```

evaluates to:

```haskell
[3, 7, 15, 4]
```

So `:` takes:

- one element on the left, and
- a list on the right.

That distinction is crucial.

### Lists are built from `:` and `[]`

Try:

```haskell
3 : 7 : [15, 4]
```

Because `:` associates to the right, Haskell groups this as:

```haskell
3 : (7 : [15, 4])
```

which gives:

```haskell
[3, 7, 15, 4]
```

But this:

```haskell
3 : 7 : 15 : 4
```

does not work. Eventually Haskell reaches:

```haskell
15 : 4
```

and the right side of `:` is supposed to be a list, not a number.

We can fix it by ending with an empty list:

```haskell
3 : 7 : 15 : 4 : []
```

Fully parenthesized:

```haskell
3 : (7 : (15 : (4 : [])))
```

This is not merely another quirky syntax for lists. It exposes the recursive structure underneath ordinary bracket notation.

```haskell
[3, 7, 15, 4]
```

is built from:

```haskell
3 : (7 : (15 : (4 : [])))
```

The three steps in one place:

```text
3 : [7, 15, 4]        -- ok: an element consed onto a list       =>  [3, 7, 15, 4]
3 : 7 : 15 : 4        -- error: the last : has 4 (a number) on its right
3 : 7 : 15 : 4 : []   -- ok: now every : has a list on its right  =>  [3, 7, 15, 4]
```

## What Types Can `:` Connect?

Suppose we write:

```haskell
x : xs
```

If:

```haskell
x :: Integer
```

then:

```haskell
xs :: [Integer]
```

and the whole expression also has type:

```haskell
[Integer]
```

But nothing about `:` is specific to integers.

We can also have:

```text
Char       and [Char]
Bool       and [Bool]
Animal     and [Animal]
[Integer]  and [[Integer]]
```

or even:

```text
(String, Shape) and [(String, Shape)]
```

The general pattern is:

```text
left side:  a
right side: [a]
result:     [a]
```

where `a` can stand for any type.

## Concatenating Lists with `++`

The operator `++` is different from `:`.

`:` attaches **one element** to the front of a list.

`++` concatenates **two lists**:

```haskell
[1, 3] ++ [7, 15, 4]
```

evaluates to:

```haskell
[1, 3, 7, 15, 4]
```

The type is:

```haskell
(++) :: [a] -> [a] -> [a]
```

Both inputs are lists, and their element types must match.

Because strings are lists of characters:

```haskell
"Hello " ++ "world!"
```

also works.

### A useful algebraic property

The empty list behaves as an identity for concatenation:

```haskell
xs ++ [] == xs
[] ++ xs == xs
```

This is analogous to:

```text
n + 0 = n
0 + n = n
```

Seeing these structural properties is useful. Functional data structures often have algebraic laws that can help us reason about what programs do.

## Useful Functions on Lists

Haskell has many built-in functions for working with lists. We will start with a small toolbox.

### `length`

`length` counts the elements in a list:

```haskell
length ["Hello", " world", "!"]   -- 3
length "Hello"                    -- 5
length []                         -- 0
```

Its type is:

```haskell
length :: [a] -> Int
```

There is a nice structural fact here:

```haskell
length [] == 0
```

and:

```haskell
length (xs ++ ys) == length xs + length ys
```

Concatenating the lists corresponds to adding their lengths. This is an example of an algebraic law that can help us reason about code.

### `head` and `tail`

`head` returns the first element:

```haskell
head ["Hello", ",", "world", "!"]
-- "Hello"
```

`tail` returns everything after the first element:

```haskell
tail ["Hello", ",", "world", "!"]
-- [",", "world", "!"]
```

Think again about the recursive form:

```haskell
x : xs
```

Then:

```haskell
head (x : xs) == x
tail (x : xs) == xs
```

This explains a possibly surprising example:

```haskell
tail [3]
```

gives:

```haskell
[]
```

because:

```haskell
[3] == 3 : []
```

and the tail is exactly the `[]`.

!!! warning "`head []` and `tail []`"
    What is the first element of an empty list? There isn't one.

    What is everything after the first element of an empty list? Again, there is no first element.

    So:

    ```haskell
    head []
    tail []
    ```

    both fail at runtime.

    This is one reason pattern matching will soon be preferable to blindly calling `head` and `tail`: patterns can force us to think explicitly about the empty-list case.

### `take` and `drop`

`take` keeps the first `n` elements:

```haskell
take 3 [5, 8, 9, 1, 13, 20, 3, 2]
-- [5,8,9]
```

`drop` removes the first `n` elements:

```haskell
drop 2 [5, 8, 9, 1, 13, 20, 3, 2]
-- [9,1,13,20,3,2]
```

Their types are:

```haskell
take :: Int -> [a] -> [a]
drop :: Int -> [a] -> [a]
```

### `null`

`null` asks whether a list is empty:

```haskell
null []       -- True
null [3,-7]   -- False
null ""       -- True
null "hello"  -- False
```

Again, the string examples work because strings are lists of characters.

### `elem`

`elem` asks whether a value occurs in a list:

```haskell
elem 10 [30, 33, 37]        -- False
elem '3' "CS131"            -- True
10 `elem` [5, 10, 15, 20]   -- True
```

Because `elem` is a two-argument function, we can also write it infix using backticks.

## Writing a Recursive Function on a List

Suppose Haskell did not already have `elem`.

How could we write a function that determines whether a value occurs in a list?

Let's call it:

```haskell
inList e list
```

The recursive structure of the list gives us the algorithm.

### Step 1: Find the base case

If the list is empty:

```haskell
[]
```

then `e` cannot be in it.

So:

```text
if the list is empty
    return False
```

### Step 2: Inspect the first element

If the list is nonempty and its first element is `e`, then we are done:

```text
if the first element is e
    return True
```

### Step 3: Recurse on the rest

Otherwise, the answer depends on the remainder of the list:

```text
check whether e is in the rest of the list
```

Using the functions we already know:

```haskell
inList e list =
  if null list
    then False
    else if head list == e
      then True
      else inList e (tail list)
```

The interesting part here is not that we reinvented `elem`. The interesting part is the **shape of the reasoning**:

- empty list gives the base case,
- nonempty list lets us inspect one element,
- recursive call handles the rest.

That structure will become much cleaner once we introduce pattern matching.

    ```haskell
    inList 9 [1,2,3,4]

    ```

    You have now implemented a simplified version of something built into the language.

## From Repetition to Abstraction: `map`

Now suppose we want to add `3` to every element of a list.

We might write:

```haskell
add3List :: [Integer] -> [Integer]
add3List list =
  if null list
    then list
    else (+ 3) (head list) : add3List (tail list)
```

Then perhaps we want to double every element:

```haskell
doubleList :: [Integer] -> [Integer]
doubleList list =
  if null list
    then list
    else (* 2) (head list) : doubleList (tail list)
```

And then add an exclamation point to every string:

```haskell
emphasizeList :: [String] -> [String]
emphasizeList list =
  if null list
    then list
    else (++ "!") (head list) : emphasizeList (tail list)
```

These functions look suspiciously similar.

!!! note "Pause and identify the pattern - nothing to submit"
    Compare the three definitions.

    What varies?

    What stays exactly the same?

The only meaningful difference is the function applied to each element:

```haskell
(+ 3)
(* 2)
(++ "!")
```

Everything else is the same recursion scaffold.

This gives us a recurring computer science lesson:

> **Where there is a pattern, there is an opportunity for abstraction.**

Instead of hard-coding the operation, make the operation itself a parameter:

```haskell
applyFuncToList f list =
  if null list
    then list
    else f (head list) : applyFuncToList f (tail list)
```

But Haskell already provides this abstraction. It is called **`map`**:

```haskell
map :: (a -> b) -> [a] -> [b]
```

For example:

```haskell
doubler x = 2 * x
map doubler [5, 7, 13]
-- [10,14,26]
```

Now remember Module 02.2: functions are values, and we can partially apply operators.

So we do not need to give `doubler` a name at all.

### `map` can change the element type

Notice the type again:

```haskell
map :: (a -> b) -> [a] -> [b]
```

The input list contains `a`s.

The output list contains `b`s.

They do **not** need to be the same type.

For example:

```haskell
map length ["Haskell", "Python", "Java"]
-- [7,6,4]
```

The input is:

```haskell
[String]
```

and the output is:

```haskell
[Int]
```

because:

```haskell
length :: [a] -> Int
```

In this particular use, each input element is a `String`, and each result is an `Int`.

## `filter`: Keep the Elements That Pass a Test

Another extremely common list pattern is to keep only elements satisfying some condition.

Haskell's `filter` function has type:

```haskell
filter :: (a -> Bool) -> [a] -> [a]
```

The first argument is a **predicate**, meaning a function that returns `Bool`.

Examples:

```haskell
filter even [8, -13, 25, 16, 0, 2]
-- [8,16,0,2]
```

```haskell
filter (< 3) [8, -13, 25, 16, 0, 2]
-- [-13,0,2]
```

```haskell
filter ((< 3) . length) ["oh", "hi", "there!"]
-- ["oh","hi"]
```

Notice an important difference between `map` and `filter`.

`map` transforms each element and preserves the number of elements.

`filter` preserves the elements themselves but may remove some of them.

There are many other useful list functions, including:

```text
minimum
maximum
sum
product
```

When you are working with lists, it is worth asking whether Haskell already provides the operation you need. Unless an assignment specifically asks you to implement something yourself, using existing list operations is encouraged.

## Pattern Matching: Use the Shape of the Data

So far we have built lists using `:`.

Now we get one of Haskell's most important ideas:

> When `:` appears in a **pattern**, it can take a list apart.

Consider:

```haskell
firstInt : otherInts = [13, 10, 20, 7]
```

The pattern on the left has the shape:

```haskell
firstInt : otherInts
```

The value on the right can be thought of as:

```haskell
13 : 10 : 20 : 7 : []
```

Haskell matches the pieces:

```text
firstInt   = 13
otherInts  = [10,20,7]
```

The syntax used to **construct** a list is therefore also useful for **deconstructing** it.

![The pattern `first_int : other_ints` drawn directly above the value `13 : 10 : 20 : 7 : []`. A solid loop ties `first_int` to `13` and is labeled `Int`; a dashed loop ties `other_ints` to `10 : 20 : 7 : []` and is labeled `[Int]`.](img/03.1/cons-pattern-match.png){ width="520" }
<br>*Haskell lines the pattern up against the value one position at a time: `first_int` binds the head, `other_ints` binds the rest.*

### Matching several elements

Because `:` associates to the right, a pattern can expose more than one element:

```haskell
c1 : c2 : rest = "aloha"
```

Remember:

```haskell
"aloha" == ['a','l','o','h','a']
```

So the pattern is really matching:

```haskell
c1 : (c2 : rest)
```

against:

```haskell
'a' : ('l' : ['o','h','a'])
```

## `case` Expressions

Pattern matching is useful whenever our computation depends on the **shape** of a value.

A `case` expression lets us provide several patterns:

```haskell
case b of
  True  -> "yep!"
  False -> "nope!"
```

If `b` is `True`, the first branch is chosen. If it is `False`, the second branch is chosen.

We can match literal values too:

```haskell
case n of
  5  -> "I love 5!"
  10 -> "10 is okay"
  _  -> "I do not know that number"
```

The underscore `_` is a **wildcard pattern**. It matches anything, but does not bind a name.

### Patterns must make sense for the value's type

This is invalid:

```haskell
case 14 of
  True  -> "yep!"
  False -> "nope!"
```

The value being matched is numeric, but the patterns `True` and `False` have type `Bool`.

![A GHCi error for `case 14 of { True -> "yep!"; False -> "nope!" }`. The message reads "No instance for (Num Bool) arising from the literal '14'", then quotes the offending `case` expression.](img/03.1/case-branch-type-error.png){ width="640" }
<br>*The value `14` is numeric, but the patterns `True` and `False` demand that it be a `Bool`.*

### Patterns should cover the possible inputs

This expression is also dangerous:

```haskell
case n of
  5  -> "I love 5!"
  10 -> "10 is okay"
```

If `n` is `100`, neither pattern matches. A non-exhaustive match can fail at runtime.

Adding:

```haskell
_ -> "I do not know that number"
```

provides a catch-all case.

![A runtime error printed by a running program: "*** Exception: case.hs:(30,17)-(32,22): Non-exhaustive patterns in case".](img/03.1/non-exhaustive-pattern-error.png){ width="520" }
<br>*Without a catch-all branch, a value that matches none of the patterns is a runtime crash, not a compile-time error.*

## Pattern Matching on Lists

Lists have exactly the recursive structure we need for pattern matching.

A list is either:

```haskell
[]
```

or:

```haskell
x : xs
```

That means many recursive list functions can be written with those two patterns.

### `myLength` with a `case`

Earlier we could write:

```haskell
myLength lst =
  if lst == []
    then 0
    else 1 + myLength (tail lst)
```

Using a `case`:

```haskell
myLength lst =
  case lst of
    []     -> 0
    (_:xs) -> 1 + myLength xs
```

The patterns describe exactly the two shapes a list can have.

Notice the wildcard:

```haskell
_:xs
```

We do not care what the first element is. We only need to know that there *is* one, and then recursively compute the length of the rest.

### Pattern matching directly in a function definition

Haskell lets us go one step further:

```haskell
myLength []     = 0
myLength (_:xs) = 1 + myLength xs
```

This is the same structure, but the pattern matching has moved directly into the function definition.

Read it almost like a mathematical definition:

> The length of the empty list is `0`.

> The length of a nonempty list is `1` plus the length of its tail.

This is one reason recursion can feel unusually natural in Haskell: the program follows the structure of the data.

### Another example: `myFilter`

Using `case`:

```haskell
myFilter test lst =
  case lst of
    []     -> []
    (x:xs) ->
      if test x
        then x : myFilter test xs
        else myFilter test xs
```

Using pattern matching in the function definition:

```haskell
myFilter _ [] = []

myFilter test (x:xs) =
  if test x
    then x : myFilter test xs
    else myFilter test xs
```

The empty-list case gives the base case. The nonempty-list case gives us exactly the two pieces we need: the first element `x` and the remaining list `xs`.

!!! note "A pattern to remember"
    When writing a recursive function on a list, try starting with:

    ```haskell
    f [] = ...
    f (x:xs) = ...
    ```

    Then ask:

    - What is the right answer for the empty list?
    - What should I do with `x`?
    - How can I use the recursive result on `xs`?

That template will carry you surprisingly far.

## Lists Are Lazy Too

Module 02.2 introduced lazy evaluation. Lists give us one of the most striking uses of it.

Haskell can represent:

```haskell
[1..]
```

an infinite list of integers.

Obviously Haskell cannot finish constructing every integer before doing anything else.

But under lazy evaluation, it does not need to.

We can ask:

```haskell
take 5 [1..]
```

and get:

```haskell
[1,2,3,4,5]
```

Only the portion demanded by `take 5` needs to be produced.

This is a nice concrete example of why lazy evaluation changes what kinds of data structures are convenient to express.

!!! example "Try it in ghci - nothing to submit"
    Try:

    ```haskell
    take 10 [1..]
    take 8 [2,4..]
    take 5 (map (* 10) [1..])
    ```

    Do **not** ask `ghci` to print `[1..]` by itself unless you are prepared to interrupt it.

## Tuples: Grouping Different Types

Lists are useful when we want any number of elements of the **same type**.

Sometimes we want a fixed collection whose pieces have **different types**.

For that, Haskell has **tuples**.

For example:

```haskell
prof1 = ("Lucas Bang", 131, False)
prof2 = ("Ben Wiedermann", 131, True)
```

Each tuple contains:

1. a `String`,
2. a number representing a course, and
3. a `Bool`.

Unlike lists, tuples:

- may contain different types,
- have a fixed number of positions, and
- include their number and order of component types in the tuple type.

For example, a value like:

```haskell
("Lucas Bang", 131, False)
```

might have a type such as:

```haskell
(String, Integer, Bool)
```

A pair such as:

```haskell
("hello", True)
```

has a different tuple type:

```haskell
(String, Bool)
```

Tuples with different numbers of components are different kinds of types.

## Pattern Matching on Tuples

Pattern matching works beautifully on tuples too.

Suppose:

```haskell
prof1 = ("Lucas Bang", 131, False)
```

Then:

```haskell
(name, course, acted) = prof1
```

matches each position and binds:

```text
name   = "Lucas Bang"
course = 131
acted  = False
```

The pattern has the same structure as the value.

We can use tuple patterns directly in function definitions:

```haskell
isRightTriangle :: (Integer, Integer, Integer) -> Bool
isRightTriangle (a, b, c) = a * a + b * b == c * c
```

Then:

```haskell
isRightTriangle (5,12,13)  -- True
isRightTriangle (3,4,5)    -- True
isRightTriangle (3,4,6)    -- False
```

If we only care about one position, wildcards help:

```haskell
getCourse (_, course, _) = course
```

Then:

```haskell
getCourse prof2
-- 131
```

<br>*A tuple pattern has the same shape as the tuple it matches: each name binds the value in its position.*

## Parameterized Types

We have been quietly using **type variables** throughout the module.

Now let's make the idea explicit.

Ask `ghci` for these types:

```text
> :type (:)
(:) :: a -> [a] -> [a]

> :type (++)
(++) :: [a] -> [a] -> [a]

> :type map
map :: (a -> b) -> [a] -> [b]

> :type filter
filter :: (a -> Bool) -> [a] -> [a]
```

The lowercase names `a` and `b` are **type variables**.

They stand for types that are not fixed in advance.

### Same letter means same type

Consider:

```haskell
(:) :: a -> [a] -> [a]
```

If `a` is `Bool`, the type becomes:

```haskell
Bool -> [Bool] -> [Bool]
```

If `a` is `Char`:

```haskell
Char -> [Char] -> [Char]
```

If `a` is `[Integer]`:

```haskell
[Integer] -> [[Integer]] -> [[Integer]]
```

The key rule is:

> Every occurrence of the same type variable within one use must be instantiated consistently.

That is why:

```haskell
True : [False, True]
```

works, while trying to cons a `Bool` onto a list of `Char`s does not.

### Different letters may be different types

Now consider:

```haskell
map :: (a -> b) -> [a] -> [b]
```

There are two type variables, `a` and `b`.

They may happen to be the same:

```haskell
map (* 2) [1,2,3]
```

takes numbers to numbers.

But they need not be:

```haskell
map show [1,2,3]
```

takes numbers to strings.

Or:

```haskell
map even [1,2,3]
```

takes numbers to `Bool`s.

This is why `map` is so general.

### A list type is parameterized

Think about:

```haskell
[a]
```

It describes a list whose element type is not yet specified.

We can instantiate that parameter in many ways:

```haskell
[Integer]
[Bool]
[Char]
[String]
[(String, Bool)]
[[Integer]]
```

So `[a]` describes a whole **family of list types**, parameterized by the element type.

This notion of parameterized types is going to become even more important when we start defining our **own** data types.

![The pattern `x : xs` with an arrow to each side: "The left side has type a" and "The right side has type [a]", joined underneath by a bracket labeled "Must match!". A caption reads "In this instance, a is a type variable and can stand for any type."](img/03.1/cons-type-variable.png){ width="600" }
<br>*All those concrete rows collapse into one signature — `(:) :: a -> [a] -> [a]` — with both `a`s required to agree.*

## Reading the Types of `head` and `tail`

Let's finish by deriving two types rather than memorizing them.

### What must `head` do?

`head` consumes a list:

```haskell
head [10,20,30]
```

and returns one element:

```haskell
10
```

If the input has type:

```haskell
[a]
```

then one element has type:

```haskell
a
```

So:

```haskell
head :: [a] -> a
```

### What must `tail` do?

`tail` also consumes a list:

```haskell
tail [10,20,30]
```

but returns another list:

```haskell
[20,30]
```

If the input has type `[a]`, the remainder still has type `[a]`.

So:

```haskell
tail :: [a] -> [a]
```

## How the Pieces Fit Together

This module introduced several ideas, but they reinforce one another.

### Lists expose recursive structure

A list is:

```haskell
[]
```

or:

```haskell
x : xs
```

That gives recursive functions a natural base case and recursive case.

### Pattern matching lets programs follow that structure directly

Instead of repeatedly asking:

```haskell
null list
head list
tail list
```

we can say:

```haskell
f [] = ...
f (x:xs) = ...
```

The structure of the program mirrors the structure of the data.

### Higher-order functions abstract recurring recursion patterns

Functions such as `map` and `filter` capture common ways of recursively traversing lists.

Instead of rewriting the traversal every time, we supply the part that varies: another function.

### Parameterized types describe the abstraction

Types such as:

```haskell
map :: (a -> b) -> [a] -> [b]
```

tell us that the same list-processing structure works for many different element types.

### Tuples give us a complementary kind of structure

Lists are homogeneous and variable-length.

Tuples are fixed-length and can combine different types.

Pattern matching works on both.

These ideas give us a much richer vocabulary for organizing programs than "variables plus loops." We can think about the **shape of data**, write functions that mirror that shape, and then abstract repeated computation patterns into reusable higher-order functions.
