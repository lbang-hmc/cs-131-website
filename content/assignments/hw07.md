# HW 7: Discovering Monads by Building Interpreters

Here's the question for this assignment: what happens when you take a simple evaluator and ask it to do just one more thing, like report errors, count operations, or keep a log of what it did? Why does so much of the code suddenly turn into bookkeeping?

You'll write **four versions of one tiny evaluator**, each doing one extra job, and then rewrite all four in monadic style. Along the way, the same pattern shows up in three problems that look completely different. The language has only integers and division, so there's nothing to distract from how the evaluator is built.

Like [Lab 7](../labs/lab07.md), this assignment is a staircase. This time the steps are evaluators instead of small functions, and the payoff is the same: by the end, `>>=` should feel like something you *invented* to get rid of repeated code, not something handed to you.

## Part 0: The Smallest Possible Language

Every evaluator in this homework works on the same abstract syntax tree (AST):

```haskell
data Term
  = Num Int
  | Div Term Term
  deriving (Show, Eq)
```

`Num n` is an integer literal. `Div t u` means: evaluate `t` and `u`, then divide the first result by the second using integer division (Haskell's `div`).

The starter file includes some sample terms:

```haskell
tOk :: Term
tOk = Div (Div (Num 1999) (Num 2)) (Num 23)

tBad :: Term
tBad = Div (Num 1) (Num 0)

tNested :: Term
tNested = Div (Div (Num 8) (Num 2)) (Num 2)
```

In ordinary arithmetic, `tOk` is:

```text
(1999 `div` 2) `div` 23
       999       `div` 23
                43
```

You'll use these terms throughout. `tBad` is the interesting one: it separates evaluators that *crash* on division by zero from evaluators that **represent failure as data**.

## Part 2: Error Reporting, `evalSafe`

Now let's make the evaluator handle division by zero *without crashing*. It should return an ordinary value that describes either success or failure:

```haskell
data SafeResult a
  = Exception String
  | Value a
  deriving (Show, Eq)
```

`SafeResult Int` is either an integer or an explanatory error message: `Value 43`, or `Exception "division by zero"`.

### Step 2.1: The Division Check

Implement:

```haskell
safeDiv :: Int -> Int -> SafeResult Int
```

It returns `Exception "division by zero"` for a zero denominator, and otherwise `Value` holding the integer quotient.

### Step 2.2: An Evaluator That Handles Errors Explicitly

Implement:

```haskell
evalSafe :: Term -> SafeResult Int
```

For `Num n`, return `Value n`. For `Div t u`:

1. Call `evalSafe t`.
2. If it fails, return the same `Exception` immediately.
3. If it succeeds, call `evalSafe u`.
4. If that fails, return its `Exception` immediately.
5. If both succeeded, call `safeDiv` on the two integers.

Use nested `case` expressions. **Don't use `>>=`, `do`, or any other monadic shortcut yet.** The point is to see the repetition before you hide it. Here is the *shape* (the starter has it too):

```haskell
evalSafe (Div t u) =
  case evalSafe t of
    Exception msg -> ...
    Value a ->
      case evalSafe u of
        Exception msg -> ...
        Value b -> ...
```

!!! example "✅ Check your work (Part 2)"
    ```haskell
    safeDiv 10 2   -- Value 5
    safeDiv 10 0   -- Exception "division by zero"
    evalSafe tOk   -- Value 43
    evalSafe tBad  -- Exception "division by zero"
    ```

    Tests: `runhaskell -itest test/Spec.hs --match "Part 2"`

!!! question "Checkpoint 2"
    Compare `evalSafe` with `evalPlain`. Which lines are actually about evaluating division? Which are only about checking and passing along failures? How much longer is the recursive case?

## Part 3: Counting Divisions, `evalCount`

Forget errors for a moment. This time, the evaluator should keep track of how many successful divisions it performs.

A program could use a mutable global counter, but we can also pass an immutable counter explicitly from one computation to the next. A *counted computation*:

- receives the current counter,
- returns its ordinary result,
- and also returns the updated counter.

```haskell
newtype Counted a = Counted
  { runCounted :: Int -> (a, Int) }
```

Read `Counted a` as "a computation that produces an `a` while carrying an integer counter." The `newtype` gives it a type of its own, so later we can make it an instance of `Monad`. (A plain type synonym isn't a distinct type.)

A computation that produces `7` without changing the counter is `Counted (\count -> (7, count))`. You run one by supplying the starting counter:

```haskell
runCounted (Counted (\count -> (7, count))) 0   -- (7,0)
```

The starter also provides `runFromZero computation = runCounted computation 0`.

### Step 3.1: Thread the Counter by Hand

Implement:

```haskell
evalCount :: Term -> Counted Int
```

For `Num n`, return `n` without incrementing the counter. For `Div t u`, the sequence must be:

```text
starting count (count0)
        |
        v
run the left child
        | returns left value AND count1
        v
run the right child, starting at count1
        | returns right value AND count2
        v
calculate the division
        |
        v
return result AND count2 + 1
```

The key rule: **the right child gets the counter produced by the left child, not the original one.** The starter provides the `let` skeleton for the recursive case. Fill it in using `runCounted` and `Counted`.

!!! example "✅ Check your work (Part 3)"
    ```haskell
    runFromZero (evalCount (Num 7))   -- (7,0)
    runFromZero (evalCount tOk)       -- (43,2)
    runFromZero (evalCount tNested)   -- (2,2)
    ```

    `tOk` has two `Div` nodes, so the counter ends at 2. As with `evalPlain`, division by zero still crashes. This version is only about counting.

    Tests: `runhaskell -itest test/Spec.hs --match "Part 3"`

!!! question "Checkpoint 3"
    Trace the values of `count0`, `count1`, and `count2` in `evalCount (Div t u)`. Why can't we just evaluate the left and right subtrees independently, both starting from the original count?

## Part 4: Recording a Trace, `evalTrace`

Now forget counting. This time, the evaluator should keep a written record of its work. Instead of printing as it goes, it returns the trace as a string**, which keeps the evaluator pure:

```haskell
data Traced a = Traced String a
  deriving (Show, Eq)
```

A traced result holds *(the accumulated text, the computed value)*. The starter provides a helper:

```haskell
traceLine :: Term -> Int -> String
traceLine term n =
  "eval(" ++ show term ++ ") = " ++ show n ++ "\n"
```

### Step 4.1: Concatenate the Log by Hand

Implement:

```haskell
evalTrace :: Term -> Traced Int
```

For `Num n`, return `n` and a line saying it was evaluated. For `Div t u`:

1. Evaluate the left child, giving a value and some log text.
2. Evaluate the right child, giving another value and more log text.
3. Compute the quotient.
4. Concatenate the left trace, the right trace, and a line for this division, **in that order**.
5. Return that trace and the quotient together.

The starter gives you a `let` skeleton for this case too.

**Why does order matter?** String concatenation isn't commutative. Swapping left and right changes the trace even when the final number stays the same.

!!! example "✅ Check your work (Part 4)"
    ```haskell
    evalTrace (Num 7)
    -- Traced "eval(Num 7) = 7\n" 7

    traceSummary (evalTrace tOk)
    -- (43,5)
    ```

    `traceSummary` (provided) gives the value and the number of trace lines. The five lines are three number leaves and two divisions. To see the whole trace, try `let Traced text _ = evalTrace tOk in putStr text`. Using `putStr` shows each `\n` as a real line break. This version still crashes on division by zero too, because we're adding one extra behavior at a time.

    Tests: `runhaskell -itest test/Spec.hs --match "Part 4"`

!!! question "Checkpoint 4"
    Compare `evalPlain`, `evalSafe`, `evalCount`, and `evalTrace`. Find the common "evaluate left, evaluate right, divide" structure. For each of the last three, write down the *extra plumbing* that makes its recursive case more complicated.

!!! warning "Stop and compare before continuing"
    This is the most important observation in the assignment, so don't rush past it.

    The essential recursive algorithm has barely changed. But depending on the result type, the code has turned into a nest of error checks, a chain of hand-threaded counters, or a tangle of log concatenations.

    What we want is to write **the common computation once**, and put each kind of extra behavior in a reusable operation.

## Part 5: Discovering the Abstraction with `SafeResult`

Start with the easiest kind of bookkeeping: failure. Look again at the shape that kept repeating in Part 2:

```haskell
case earlierResult of
  Exception msg -> Exception msg
  Value x       -> nextStep x
```

None of the error-handling logic depends on *which* computation comes next.

### Step 5.1: Put an Ordinary Value into a Result

Implement `safePure :: a -> SafeResult a`, which represents an ordinary successful result: `safePure 5` is `Value 5`.

### Step 5.2: Connect One Result to the Next

Implement:

```haskell
safeBind :: SafeResult a
         -> (a -> SafeResult b)
         -> SafeResult b
```

The type is worth reading slowly:

```text
SafeResult a  ->  (a -> SafeResult b)  ->  SafeResult b
    ^                     ^                    ^
 earlier work      function describing      combined result
                   what to do next
```

The next function expects a plain `a`, not a `SafeResult a`. `safeBind` resolves that mismatch:

- On `Exception msg`, pass the error along and *don't* call the next function.
- On `Value x`, call the next function with `x`.

```haskell
safeBind (Value 7) (\x -> Value (x + 1))           -- Value 8
safeBind (Exception "oops") (\x -> Value (x + 1))  -- Exception "oops"
```

In the second example, the lambda is never called.

### Step 5.3: Refactor the Evaluator, Before Any Typeclass

Implement:

```haskell
evalSafeWithBind :: Term -> SafeResult Int
```

Use `safePure` for `Num`, and two calls to `safeBind` for `Div`. **No nested `case` expressions.** Use `safeDiv` for the final step, the one that might fail. The recipe:

```text
evaluate left
  THEN take its successful value a
  evaluate right
    THEN take its successful value b
    safely divide a by b
```

Compare the result to `evalSafe`. The evaluator is about what the language *means* again, and `safeBind` owns the failure handling.

!!! example "✅ Check your work (Part 5)"
    ```haskell
    safePure 5                                         -- Value 5
    safeBind (Value 7) (\x -> Value (x + 1))           -- Value 8
    safeBind (Exception "oops") (\x -> Value (x + 1))  -- Exception "oops"
    evalSafeWithBind tOk                               -- Value 43
    evalSafeWithBind tBad                              -- Exception "division by zero"
    ```

    Tests: `runhaskell -itest test/Spec.hs --match "Part 5"`

!!! question "Checkpoint 5"
    Explain why ``safePure (a `div` b)`` is **not** a substitute for `safeDiv a b`. Where does the actual division-by-zero check belong?

## Part 6: Making `SafeResult` a Real Monad

You've now invented two operations with very general-looking types:

```haskell
safePure :: a -> SafeResult a
safeBind :: SafeResult a -> (a -> SafeResult b) -> SafeResult b
```

Haskell's standard names for these are:

```haskell
pure  :: Applicative m => a -> m a
(>>=) :: Monad m => m a -> (a -> m b) -> m b
```

`>>=` is pronounced "bind". (Wadler calls `pure` "`unit`", and older code often uses `return`. This assignment always uses `pure`.)

Why is `pure` in `Applicative` and not `Monad`? Haskell organizes these interfaces in a hierarchy:

```text
Functor           fmap
    |
Applicative       pure, (<*>)
    |
Monad             (>>=)
```

`(<*>)` applies a wrapped function to a wrapped value. For example, `Value (+1) <*> Value 2` is `Value 3`. In this assignment you mostly need it because Haskell won't accept a `Monad` instance unless there's an `Applicative` instance too. You met `Functor` in [Module 7.1](../modules/07.1-functors-generalizing-map.md), and this homework doesn't turn into an `Applicative` tutorial.

### Step 6.1: Three Instances for `SafeResult`

Complete the `Functor`, `Applicative`, and `Monad` instances in the starter:

- **`Functor`**: the same idea as `fmap` on `Maybe`. Transform the value in `Value x`, and leave an `Exception` unchanged.
- **`Applicative`**: `pure` behaves like `safePure`. `Exception msg <*> anything` keeps that error. `Value f <*> result` applies `f` to the value inside `result`, if there is one. You can use `fmap` for this.
- **`Monad`**: reuse exactly the two cases you discovered in `safeBind`. It should look almost identical.

!!! note "These instances are for your own type"
    You can define instances for `SafeResult` because you created the type. Don't try to redefine Haskell's existing `Monad Maybe` instance.

### Step 6.2: Rewrite the Evaluator a Third Time

Implement:

```haskell
evalSafeM :: Term -> SafeResult Int
```

This time use `pure` and `>>=`, or the equivalent `do` notation, and finish with `safeDiv`. The evaluator should **never inspect `Exception` or `Value` directly**.

```haskell
Value 7 >>= \x -> Value (x + 1)           -- Value 8
Exception "oops" >>= \x -> Value (x + 1)  -- Exception "oops"
```

### Step 6.3: Check a Monad Law

The *right identity law* says:

```haskell
m >>= pure  ==  m
```

Try it for both constructors:

```haskell
(Value 7 >>= pure) == Value 7                                         -- True
(Exception "oops" >>= pure) == (Exception "oops" :: SafeResult Int)   -- True
```

### Step 6.4: A Tiny Bridge Back to the Plain Evaluator

Wadler also treats the simplest computation, one that carries *no* extra information, as a monad. The starter provides it, instances included:

```haskell
newtype Plain a = Plain { unPlain :: a }
  deriving (Show, Eq)

-- its bind just passes the value along:
--   Plain x >>= next = next x
```

Your job is just to write:

```haskell
evalPlainM :: Term -> Plain Int
```

using `pure` and `do` notation. It should mirror `evalSafeM` almost exactly, except that its last step can use ordinary `div`, because it has no error reporting. This version adds almost no behavior. It's there so the comparison of *all four* monadic evaluators is complete.

!!! example "✅ Check your work (Part 6)"

    ```haskell
    evalSafeM tBad             -- Exception "division by zero"
    unPlain (evalPlainM tOk)   -- 43
    ```

## Part 7: The Same Idea for the Counter

Now return to the counter threading from Part 3. A `Counted a` is, underneath, an `Int -> (a, Int)`. The first counter goes to the computation that runs first, and the next computation must receive *its* updated counter.

### Step 7.1: Finish the Instances for `Counted`

To keep the focus on sequencing, the starter provides `fmap` and `<*>`. You implement `pure` (in the `Applicative` instance) and `>>=` (in the `Monad` instance). Your bind should:

1. Run `first` on the incoming counter.
2. Get back an ordinary result `a` and the updated counter.
3. Call `next a` to get the *next counted computation*.
4. Run that computation on the updated counter.
5. Return its result and final counter.

The key point: **bind handles passing the counter from one computation to the next.** The evaluator no longer needs to name `count0`, `count1`, and `count2`.

### Step 7.2: One Useful Counted Operation

The starter provides:

```haskell
tick :: Counted ()
tick = Counted (\count -> ((), count + 1))
```

`tick` increments the counter without producing an interesting value. The value `()` means "nothing useful to report." Its type is also `()`.

### Step 7.3: Rewrite the Evaluator

Implement:

```haskell
evalCountM :: Term -> Counted Int
```

using `do` notation, `pure` for the ordinary result, and `tick` to count the division:

```text
a <- evaluate left
b <- evaluate right
tick
pure the quotient
```

!!! example "✅ Check your work (Part 7)"
    ```haskell
    runFromZero (evalCount tOk)    -- (43,2)
    runFromZero (evalCountM tOk)   -- (43,2)
    runCounted (evalCountM tOk) 10 -- (43,12)
    ```

    Tests: `runhaskell -itest test/Spec.hs --match "Part 7"`

!!! question "Checkpoint 7"
    Compare `evalCountM` and `evalSafeM`. What is structurally the same in the recursive case? What differs? Where did the explicit counter plumbing go?

## Part 8: The Same Idea for Traces

The third variation produced both a value and some log text, `Traced "some log text" 42 :: Traced Int`.

### Step 8.1: Finish the Instances for `Traced`

The starter provides `fmap` and `<*>`. You implement `pure` and `>>=`:

`pure` produces the value with an empty log. Your bind should:

1. Start with the first traced result, which has text `text1` and value `x`.
2. Call the next function with `x`.
3. Get back text `text2` and the next value.
4. Return the combined trace `text1 ++ text2` with the next value.

It's the same *type pattern* as error handling and counting, but the bookkeeping is different.

### Step 8.2: One Useful Traced Operation

The starter provides:

```haskell
record :: String -> Traced ()
record message = Traced message ()
```

`record` is a small computation whose only job is to add a message to the trace.

### Step 8.3: Rewrite the Evaluator

Implement:

```haskell
evalTraceM :: Term -> Traced Int
```

For `Num n`, record a line for the number and return `n`. For `Div t u`, use `do` notation:

```text
a <- evaluate left
b <- evaluate right
let result = a `div` b
record a line about this division
pure result
```

!!! example "✅ Check your work (Part 8)"
    ```haskell
    evalTraceM (Num 7)              -- Traced "eval(Num 7) = 7\n" 7
    traceSummary (evalTraceM tOk)   -- (43,5)
    evalTraceM tOk == evalTrace tOk -- True
    ```

    Tests: `runhaskell -itest test/Spec.hs --match "Part 8"`

!!! question "Checkpoint 8"

## Part 9: Seeing the Common Computation Again

Put your four monadic division cases side by side: `evalPlainM`, `evalSafeM`, `evalCountM`, and `evalTraceM`. Each should have this recognizable shape:

```haskell
do
  a <- eval... t
  b <- eval... u
  -- possibly one piece of variation-specific work
  -- produce a result
```

**This is the point of the homework.** Your original evaluators had to spell out how to *carry* the extra information through every recursive call. In the monadic versions, **the `Monad` instance does that repeated plumbing**, and the evaluator can focus on the essential sequence again: evaluate left, then evaluate right, then divide.

You'll fill in this table on Gradescope (see [Turning It In](#turning-it-in)):

| Evaluator | What extra information does it carry? | Where is the bookkeeping in the manual version? | Where does it live in the monadic version? |
|---|---|---|---|
| `evalPlain` / `evalPlainM` | ... | ... | ... |
| `evalSafe` / `evalSafeM` | ... | ... | ... |
| `evalCount` / `evalCountM` | ... | ... | ... |
| `evalTrace` / `evalTraceM` | ... | ... | ... |

### Step 9.1: Three Laws, Intuitively

You checked right identity for `SafeResult`. A monad must satisfy three laws:

**Left identity.** Wrapping an ordinary value with `pure` and then passing it to `f` is the same as just calling `f`:

```haskell
pure x >>= f  =  f x
```

**Right identity.** Taking the ordinary result and re-wrapping it changes nothing:

```haskell
m >>= pure  =  m
```

**Associativity.** Changing the *grouping* of a chain doesn't change its behavior. It does *not* mean you can reorder the computations:

```haskell
(m >>= f) >>= g  =  m >>= (\x -> f x >>= g)
```

The tests check examples of all three laws (`--match "Monad law"`), but on Gradescope you'll show one check you did yourself.

!!! question "Checkpoint 9: a law check"
    Choose one law other than right identity. Test it with concrete values for `SafeResult` or `Traced`, and explain why both sides agree. For `Counted`, run both sides from the same starting counter and compare: `Counted` wraps a function, so it has no `Eq` instance.

### Step 9.2: What This All Shows

The common interface is just two operations:

```haskell
pure  :: a -> m a
(>>=) :: m a -> (a -> m b) -> m b
```

But `pure` and `>>=` do different things for different `m`s:

- `SafeResult`: keep errors, and skip later steps after a failure.
- `Counted`: carry the updated counter into the next step.
- `Traced`: accumulate log text, in order.

**Monads don't automatically mean mutable state, exceptions, or logging.** Each monad's instance defines how *its* computations are connected. That's the abstraction Wadler uses to make changes to an evaluator modular.

Every result type so far added *one* extra behavior. Real programs often want several. Try combining safe division and counting in a single type. One starting point:

```haskell
newtype SafeCount a = SafeCount
  { runSafeCount :: Int -> (SafeResult a, Int) }
```

Define a combined `pure` and bind (as named helpers or as full instances), and write `evalSafeCount :: Term -> SafeCount Int`.

We recommend counting successful divisions. When a division fails, keep the error, stop evaluating later steps, and keep the count of the divisions that succeeded before it. The starter defines:

```haskell
bonusExample :: Term
bonusExample = Div (Div (Num 12) (Num 3)) (Num 0)
```

The inner division succeeds and the outer one fails, so running from counter `0` should give something equivalent to `(Exception "division by zero", 1)`.

Questions to think about:

- Which pieces of your earlier code can you reuse?
- What should bind do if the first computation returned an `Exception`?
- Should a failed division count as an *attempted* division? What would you change if that were the spec?
- Does your combined bind satisfy right identity and associativity?

## Where to Go From Here

**The most important takeaway:** we started with an evaluator whose real algorithm was a few lines long. Adding useful features buried it under repeated bookkeeping. By discovering `pure` and `>>=`, we made that bookkeeping reusable and got the simple evaluator back.

Now's a good time to read Wadler's [*Monads for Functional Programming*](https://homepages.inf.ed.ac.uk/wadler/papers/marktoberdorf/baastad.pdf). Section 2 will feel familiar. Section 3 states the monad laws properly. Section 5 builds a **parser** as a monad, which is the same idea behind the parser combinators you used in [HW 6](hw06.md): a parser is a computation that carries "the rest of the input" and might fail. If the bonus made you wonder how to combine several behaviors without writing a new monad by hand every time, look up **monad transformers**.
