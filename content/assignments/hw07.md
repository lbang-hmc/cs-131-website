## Part 0: The Smallest Possible Language

Every evaluator in this homework works on the same abstract syntax tree (AST):

```haskell
data Term
  = Num Int
  | Div Term Term
  deriving (Show, Eq)
```

`Num n` is an integer literal. `Div t u` means: evaluate `t` and `u`, then divide the first result by the second using integer division (Haskell's `div`).

`HW07.hs` includes some sample terms:

```haskell
tOk :: Term
tOk = Div (Div (Num 1999) (Num 2)) (Num 23)

tBad :: Term
tBad = Div (Num 1) (Num 0)

tNested :: Term
tNested = Div (Div (Num 8) (Num 2)) (Num 2)
```

In ordinary arithmetic, `tOk` is:

```text
(1999 `div` 2) `div` 23
       999       `div` 23
                43
```

You'll use these terms throughout. `tBad` is the interesting one: it separates evaluators that crash on division by zero from evaluators that represent failure as data.

## Part 2: Error Reporting, `evalSafe`

Now let's make the evaluator handle division by zero *without crashing*. It should return an ordinary value that describes either success or failure:

```haskell
data SafeResult a
  = Exception String
  | Value a
  deriving (Show, Eq)
```

`SafeResult Int` is either an integer or an explanatory error message: `Value 43`, or `Exception "division by zero"`.

### Step 2.1: The Division Check

Implement:

```haskell
safeDiv :: Int -> Int -> SafeResult Int
```

It returns `Exception "division by zero"` for a zero denominator, and otherwise `Value` holding the integer quotient.

### Step 2.2: An Evaluator That Handles Errors Explicitly

Implement:

```haskell
evalSafe :: Term -> SafeResult Int
```

For `Num n`, return `Value n`. For `Div t u`:

1. Call `evalSafe t`.
2. If it fails, return the same `Exception` immediately.
3. If it succeeds, call `evalSafe u`.
4. If that fails, return its `Exception` immediately.
5. If both succeeded, call `safeDiv` on the two integers.

Use nested `case` expressions. **Don't use `>>=`, `do`, or any other monadic shortcut yet.** The point is to see the repetition before you hide it. Here is the *shape* (`HW07.hs` has it too):

```haskell
evalSafe (Div t u) =
  case evalSafe t of
    Exception msg -> ...
    Value a ->
      case evalSafe u of
        Exception msg -> ...
        Value b -> ...
```

!!! example "✅ Check your work (Part 2)"
    ```haskell
    safeDiv 10 2   -- Value 5
    safeDiv 10 0   -- Exception "division by zero"
    evalSafe tOk   -- Value 43
    evalSafe tBad  -- Exception "division by zero"
    ```

    Tests: `runhaskell -itest test/Spec.hs --match "Part 2"`

!!! question "Checkpoint 2"
    Compare `evalSafe` with `evalPlain`. Which lines are actually about evaluating division? Which are only about checking and passing along failures? How much longer is the recursive case?

## Part 3: Counting Divisions, `evalCount`

This version ignores errors. Instead, it keeps track of how many successful divisions it performs.

A program could use a mutable global counter, but we can also pass an immutable counter explicitly from one computation to the next. A *counted computation*:

- receives the current counter,
- returns its ordinary result,
- and also returns the updated counter.

```haskell
newtype Counted a = Counted (Int -> (a, Int))
```

Read `Counted a` as "a computation that produces an `a` while carrying an integer counter." A `newtype` is like a `data` declaration with exactly one constructor holding exactly one thing, here a function (see the [ParserBase reference](../how-to/parser-base.md), where `Parser` is built the same way). It gives `Counted` a type of its own, so later we can make it an instance of `Monad`. A plain type synonym isn't a distinct type, so it couldn't be one.

`HW07.hs` provides a function that takes the function back out of a `Counted` and runs it on a starting counter:

```haskell
runCounted :: Counted a -> Int -> (a, Int)
runCounted (Counted f) = f
```

A computation that produces `7` without changing the counter is `Counted (\count -> (7, count))`. One that produces `"hi"` and adds 1 to the counter is `Counted (\count -> ("hi", count + 1))`. A `Counted` value is a function waiting for a starting counter. Run one with `runCounted` by supplying that counter:

```haskell
runCounted (Counted (\count -> (7, count))) 0          -- (7,0)
runCounted (Counted (\count -> ("hi", count + 1))) 0   -- ("hi",1)
runCounted (Counted (\count -> ("hi", count + 1))) 5   -- ("hi",6)
```

The same computation gives a different final count depending on where it starts.

`HW07.hs` also provides `runFromZero computation = runCounted computation 0`.

### Step 3.1: Thread the Counter by Hand

Implement:

```haskell
evalCount :: Term -> Counted Int
```

For `Num n`, return `n` without incrementing the counter. For `Div t u`, the sequence must be:

```text
starting count (count0)
        |
        v
run the left child
        | returns left value AND count1
        v
run the right child, starting at count1
        | returns right value AND count2
        v
calculate the division
        |
        v
return result AND count2 + 1
```

The right child gets the counter produced by the left child, not the original one. `HW07.hs` provides the `let` skeleton for the recursive case. Fill it in using `runCounted` and `Counted`.

!!! example "✅ Check your work (Part 3)"
    ```haskell
    runFromZero (evalCount (Num 7))   -- (7,0)
    runFromZero (evalCount tOk)       -- (43,2)
    runFromZero (evalCount tNested)   -- (2,2)
    ```

    `tOk` has two `Div` nodes, so the counter ends at 2. This version is only about counting, so it doesn't handle division by zero.

    Tests: `runhaskell -itest test/Spec.hs --match "Part 3"`

!!! question "Checkpoint 3"
    Trace the values of `count0`, `count1`, and `count2` in `evalCount (Div t u)`. Why can't we just evaluate the left and right subtrees independently, both starting from the original count? Give a concrete term where that would produce the wrong count.

## Part 4: Recording a Trace, `evalTrace`

This version ignores errors and counting, and keeps a written record of its work instead. It doesn't print as it goes. It returns the trace as a string, which keeps the evaluator pure:

```haskell
data Traced a = Traced String a
  deriving (Show, Eq)
```

A traced result holds *(the accumulated text, the computed value)*. `HW07.hs` provides a helper:

```haskell
traceLine :: Term -> Int -> String
traceLine term n =
  "eval(" ++ show term ++ ") = " ++ show n ++ "\n"
```

`traceLine` only formats a line of text. It doesn't evaluate anything, so you pass in the term and the value it should report:

```haskell
traceLine (Num 7) 7                 -- "eval(Num 7) = 7\n"
traceLine (Div (Num 8) (Num 2)) 4   -- "eval(Div (Num 8) (Num 2)) = 4\n"
putStr (traceLine (Div (Num 8) (Num 2)) 4)
-- eval(Div (Num 8) (Num 2)) = 4
```

GHCi shows a `String` with quotes and `\n`. `putStr` prints it as a line of text.

### Step 4.1: Concatenate the Log by Hand

Implement:

```haskell
evalTrace :: Term -> Traced Int
```

Make every log line with `traceLine`, so the format matches the tests. For `Num n`, return `n` and the line `traceLine (Num n) n`. For `Div t u`:

1. Evaluate the left child, giving a value and some log text.
2. Evaluate the right child, giving another value and more log text.
3. Compute the quotient.
4. Concatenate the left trace, the right trace, and a line for this division, **in that order**.
5. Return that trace and the quotient together.

`HW07.hs` gives you a `let` skeleton for this case too.

!!! example "✅ Check your work (Part 4)"
    ```haskell
    evalTrace (Num 7)
    -- Traced "eval(Num 7) = 7\n" 7

    traceSummary (evalTrace tOk)
    -- (43,5)
    ```

    `traceSummary` (provided) gives the value and the number of trace lines. The five lines are three number leaves and two divisions. To see the whole trace, try `let Traced text _ = evalTrace tOk in putStr text`. Using `putStr` shows each `\n` as a real line break. Like `evalCount`, this version doesn't handle division by zero.

    Tests: `runhaskell -itest test/Spec.hs --match "Part 4"`

## Part 5: Discovering the Abstraction with `SafeResult`

Start with the easiest kind of bookkeeping: failure. Look again at the shape that kept repeating in Part 2:

```haskell
case earlierResult of
  Exception msg -> Exception msg
  Value x       -> nextStep x
```

None of the error-handling logic depends on *which* computation comes next. So it can go in a helper that takes the earlier result and a function for the next step.

Before you read on, write down what you think that helper's type should be. Then compare your guess with Step 5.2.

### Step 5.1: Put an Ordinary Value into a Result

Implement `safePure :: a -> SafeResult a`, which represents an ordinary successful result: `safePure 5` is `Value 5`.

### Step 5.2: Connect One Result to the Next

Implement:

```haskell
safeBind :: SafeResult a
         -> (a -> SafeResult b)
         -> SafeResult b
```

Here's how the pieces of the type line up:

```text
SafeResult a  ->  (a -> SafeResult b)  ->  SafeResult b
    ^                     ^                    ^
 earlier work      function describing      combined result
                   what to do next
```

The next function expects a plain `a`, not a `SafeResult a`. `safeBind` resolves that mismatch:

- On `Exception msg`, pass the error along and *don't* call the next function.
- On `Value x`, call the next function with `x`.

```haskell
safeBind (Value 7) (\x -> Value (x + 1))           -- Value 8
safeBind (Exception "oops") (\x -> Value (x + 1))  -- Exception "oops"
```

In the second example, the lambda is never called.

!!! tip "Puzzle (optional): why not reuse the error?"
    Here is a version of `safeBind` that hands back the error it was given instead of building a new one:

    ```haskell
    safeBind result next =
      case result of
        Exception _ -> result
        Value x     -> next x
    ```

    GHC rejects it, saying that `a` and `b` don't match and that they are "rigid type variables". (*Rigid* means the type comes from the signature you wrote, so the caller picks it, not you.) Look at the type of `safeBind`. What type does `result` have, and what type must the answer have? `Exception "oops"` contains no `a`, so why does it matter? And why does writing `Exception msg` again fix it?

### Step 5.3: Refactor the Evaluator, Before Any Typeclass

Implement:

```haskell
evalSafeWithBind :: Term -> SafeResult Int
```

Use `safePure` for `Num`, and two calls to `safeBind` for `Div`. **No nested `case` expressions.** Use `safeDiv` for the final step, the one that might fail. The recipe:

```text
evaluate left
  THEN take its successful value a
  evaluate right
    THEN take its successful value b
    safely divide a by b
```

!!! tip "Hint: two lambdas, one inside the other"
    `Div` has two children to evaluate, and each result goes through its own `safeBind`. Each `safeBind` needs a function that says what to do next, so you'll write two lambdas: one that receives `a` and one that receives `b`. The second lambda goes *inside* the body of the first. That's the only way `a` is still in scope when you finally divide `a` by `b`. Each THEN in the recipe above is a `safeBind`, and the indentation shows the nesting.

Compare the result to `evalSafe`.

!!! example "✅ Check your work (Part 5)"
    ```haskell
    safePure 5                                         -- Value 5
    safeBind (Value 7) (\x -> Value (x + 1))           -- Value 8
    safeBind (Exception "oops") (\x -> Value (x + 1))  -- Exception "oops"
    evalSafeWithBind tOk                               -- Value 43
    evalSafeWithBind tBad                              -- Exception "division by zero"
    ```

    Tests: `runhaskell -itest test/Spec.hs --match "Part 5"`

!!! question "Checkpoint 5"
    Explain why ``safePure (a `div` b)`` is **not** a substitute for `safeDiv a b`. Where does the actual division-by-zero check belong?

## Part 6: Making `SafeResult` a Real Monad

You've now invented two operations with very general-looking types:

```haskell
safePure :: a -> SafeResult a
safeBind :: SafeResult a -> (a -> SafeResult b) -> SafeResult b
```

Haskell's standard names for these are:

```haskell
pure  :: Applicative m => a -> m a
(>>=) :: Monad m => m a -> (a -> m b) -> m b
```

`>>=` is pronounced "bind". (Wadler calls `pure` "`unit`", and older code often uses `return`. This assignment always uses `pure`.)

Why is `pure` in `Applicative` and not `Monad`? Haskell organizes these interfaces in a hierarchy:

```text
Functor           fmap
    |
Applicative       pure, (<*>)
    |
Monad             (>>=)
```

`(<*>)` applies a wrapped function to a wrapped value. For example, `Value (+1) <*> Value 2` is `Value 3`. In this assignment you mostly need it because Haskell won't accept a `Monad` instance unless there's an `Applicative` instance too. You met `Functor` in [Module 7.1](../modules/07.1-functors-generalizing-map.md).

### Step 6.1: Three Instances for `SafeResult`

Complete the `Functor`, `Applicative`, and `Monad` instances in `HW07.hs`:

- **`Functor`**: the same idea as `fmap` on `Maybe`. Transform the value in `Value x`, and leave an `Exception` unchanged.
- **`Applicative`**: `pure` behaves like `safePure`. `Exception msg <*> anything` keeps that error. `Value f <*> result` applies `f` to the value inside `result`, if there is one. You can use `fmap` for this.
- **`Monad`**: reuse exactly the two cases you discovered in `safeBind`. It should look almost identical.

!!! note "These instances are for your own type"
    You can define instances for `SafeResult` because you created the type. Don't try to redefine Haskell's existing `Monad Maybe` instance.

### Step 6.2: Rewrite the Evaluator a Third Time

Implement:

```haskell
evalSafeM :: Term -> SafeResult Int
```

This time use `pure` and `>>=`, or the equivalent `do` notation, and finish with `safeDiv`. The evaluator should **never inspect `Exception` or `Value` directly**.

```haskell
Value 7 >>= \x -> Value (x + 1)           -- Value 8
Exception "oops" >>= \x -> Value (x + 1)  -- Exception "oops"
```

### Step 6.3: Check a Monad Law

The *right identity law* says:

```haskell
m >>= pure  ==  m
```

Try it for both constructors:

```haskell
(Value 7 >>= pure) == Value 7                                         -- True
(Exception "oops" >>= pure) == (Exception "oops" :: SafeResult Int)   -- True
```

### Step 6.4: A Tiny Bridge Back to the Plain Evaluator

Wadler also treats the simplest computation, one that carries *no* extra information, as a monad. `HW07.hs` provides it, instances included:

```haskell
newtype Plain a = Plain a
  deriving (Show, Eq)

unPlain :: Plain a -> a
unPlain (Plain x) = x

-- its bind just passes the value along:
--   Plain x >>= next = next x
```

Your job is just to write:

```haskell
evalPlainM :: Term -> Plain Int
```

using `pure` and `do` notation. It should mirror `evalSafeM` almost exactly, except that its last step can use ordinary `div`, because it has no error reporting. This version adds almost no behavior. It's there so the comparison of *all four* monadic evaluators is complete.

!!! example "✅ Check your work (Part 6)"
    ```haskell

    evalSafeM tBad             -- Exception "division by zero"
    unPlain (evalPlainM tOk)   -- 43
    ```

## Part 7: The Same Idea for the Counter

Now return to the counter threading from Part 3. A `Counted a` is, underneath, an `Int -> (a, Int)`. The first counter goes to the computation that runs first, and the next computation must receive *its* updated counter.

### Step 7.1: One Useful Counted Operation

`HW07.hs` provides:

```haskell
tick :: Counted ()
tick = Counted (\count -> ((), count + 1))
```

`tick` increments the counter without producing an interesting value. The value `()` means "nothing useful to report." Its type is also `()`.

### Step 7.2: Factor Out the Counter Threading

Do for `Counted` what Part 5 did for `SafeResult`. Implement:

```haskell
countBind :: Counted a -> (a -> Counted b) -> Counted b
```

`countBind first next` is a counted computation. Given a starting counter, it runs `first`, passes the resulting value to `next`, and runs the computation `next` returns on the updated counter. Look at the `let` you wrote in `evalCount`. If this feels familiar, it's because `followedBy` in [Lab 7](../labs/lab07.md) did the same thing with a stack.

```haskell
runCounted (countBind tick (\_ -> tick)) 0   -- ((),2)
```

### Step 7.3: Finish the Instances for `Counted`

The provided code includes `fmap` and `<*>`. You implement `pure` (in the `Applicative` instance) and `>>=` (in the `Monad` instance). `>>=` should do exactly what `countBind` does, so `first >>= next = countBind first next` is a fine answer.

### Step 7.4: Rewrite the Evaluator

Implement:

```haskell
evalCountM :: Term -> Counted Int
```

using `do` notation, `pure` for the ordinary result, and `tick` to count the division:

```text
a <- evaluate left
b <- evaluate right
tick
pure the quotient
```

!!! example "✅ Check your work (Part 7)"
    ```haskell
    runCounted (countBind tick (\_ -> tick)) 0   -- ((),2)
    runFromZero (evalCount tOk)    -- (43,2)
    runFromZero (evalCountM tOk)   -- (43,2)
    runCounted (evalCountM tOk) 10 -- (43,12)
    ```

    Tests: `runhaskell -itest test/Spec.hs --match "Part 7"`

!!! question "Checkpoint 7"
    Compare `evalCountM` and `evalSafeM`. What is structurally the same in the recursive case? What differs? `evalCountM` never mentions a counter variable. Where did `count0`, `count1`, and `count2` go?

## Part 8: The Same Idea for Traces

The third variation produced both a value and some log text, `Traced "some log text" 42 :: Traced Int`.

### Step 8.1: Finish the Instances for `Traced`

The provided code includes `fmap` and `<*>`. You implement `pure` and `>>=`:

`pure` produces the value with an empty log. Your bind should:

1. Start with the first traced result, which has text `text1` and value `x`.
2. Call the next function with `x`.
3. Get back text `text2` and the next value.
4. Return the combined trace `text1 ++ text2` with the next value.

It's the same *type pattern* as error handling and counting, but the bookkeeping is different.

### Step 8.2: One Useful Traced Operation

`HW07.hs` provides:

```haskell
record :: String -> Traced ()
record message = Traced message ()
```

`record` is a small computation whose only job is to add a message to the trace.

### Step 8.3: Rewrite the Evaluator

Implement:

```haskell
evalTraceM :: Term -> Traced Int
```

For `Num n`, record a line for the number and return `n`. For `Div t u`, use `do` notation. It should look a lot like `evalCountM`, with `record` doing the job `tick` did there. Record the division's line after evaluating both children, so the trace comes out in the same order as `evalTrace`'s.

You'll need the quotient twice, once in the log line and once as the result. To name it, use `let` inside `do`. It has no `in`:

```haskell
do a <- ...
   b <- ...
   let q = a `div` b
   ...
```

!!! example "✅ Check your work (Part 8)"
    ```haskell
    evalTraceM (Num 7)              -- Traced "eval(Num 7) = 7\n" 7
    traceSummary (evalTraceM tOk)   -- (43,5)
    evalTraceM tOk == evalTrace tOk -- True
    ```

## Part 9: Seeing the Common Computation Again

Put your four monadic division cases side by side: `evalPlainM`, `evalSafeM`, `evalCountM`, and `evalTraceM`. Each should have this recognizable shape:

```haskell
do
  a <- eval... t
  b <- eval... u
  -- possibly one piece of variation-specific work
  -- produce a result
```

### Step 9.1: One Evaluator for All Four

The four monadic evaluators differ only in two places: what happens after a node is evaluated, and how to divide. So you can write the evaluator once, for any monad, and pass those two pieces in:

```haskell
evalWith :: Monad m
         => (Term -> Int -> m ())    -- afterNode
         -> (Int -> Int -> m Int)    -- divide
         -> Term -> m Int
```

The first argument, `afterNode`, is a function that `evalWith` calls after evaluating each node, numbers included. It gets the node and the value that node evaluated to: `afterNode (Num n) n` for a number, and `afterNode (Div t u) v` for a division that came out to `v`. It returns `m ()`, a step that produces no useful value but can do this monad's extra work. Most evaluators don't need it and pass `\_ _ -> pure ()`. The trace evaluator uses it to record a line.

The second argument, `divide`, gets the two evaluated children and produces the quotient however this monad needs. For example, the safe evaluator would pass `safeDiv`, which reports division by zero.

For `Num n`, call `afterNode` and return `n`. For `Div t u`, evaluate left, evaluate right, divide, call `afterNode` on the result, and return it.

Then get each evaluator back as a single call to `evalWith`: `evalPlainW`, `evalSafeW`, `evalCountW`, and `evalTraceW`. Each should agree with its `…M` version. Think about which hook does the extra work in each case. For some evaluators, one of the hooks does nothing (`\_ _ -> pure ()`).

!!! example "✅ Check your work (Step 9.1)"
    ```haskell
    unPlain (evalPlainW tOk)         -- 43
    evalSafeW tBad                   -- Exception "division by zero"
    runFromZero (evalCountW tOk)     -- (43,2)
    evalTraceW tOk == evalTraceM tOk -- True
    ```

    Tests: `runhaskell -itest test/Spec.hs --match "evalWith"`

Now adding a new kind of evaluator means writing an instance and two small hooks. The recursion never changes.

### Step 9.3: Three Laws, Intuitively

You checked right identity for `SafeResult`. A monad must satisfy three laws:

**Left identity.** Wrapping an ordinary value with `pure` and then passing it to `f` is the same as just calling `f`:

```haskell
pure x >>= f  =  f x
```

**Right identity.** Taking the ordinary result and re-wrapping it changes nothing:

```haskell
m >>= pure  =  m
```

**Associativity.** Changing the *grouping* of a chain doesn't change its behavior. It does *not* mean you can reorder the computations:

```haskell
(m >>= f) >>= g  =  m >>= (\x -> f x >>= g)
```

The tests check examples of all three laws (`--match "Monad law"`), but on Gradescope you'll show one check you did yourself.

!!! question "Checkpoint 9: a law check"
    Choose one law other than right identity. Test it with concrete values for `SafeResult` or `Traced`, and explain why both sides agree. For `Counted`, run both sides from the same starting counter and compare: `Counted` wraps a function, so it has no `Eq` instance.

### Step 9.4: What This All Shows

All four evaluators use the same two operations, `pure` and `>>=`, but each type's instance decides what "and then" means. Changing what an evaluator carries is a change to one instance, not to every recursive case. That's how Wadler makes changes to an evaluator modular.

### Bonus 2: Variables, Environments, and Simplifiers

The language so far has only numbers and division. If you want to keep going, here are some directions to try. Do as much or as little as you like, in a new file (say `Bonus2.hs`) so `HW07.hs` stays as you submitted it.

**Grow the language.** Make a new expression type with addition, subtraction, and multiplication alongside division. Then add variables, and a `let` form that gives a name to a value inside a smaller expression. To evaluate variables you'll need an *environment*, a record of which value each name has, and something to do when a name isn't in it. Your `SafeResult` monad is a natural fit for that. A list of pairs and the Prelude's `lookup` are enough to start. (If you import `HW07`, write `import HW07 (SafeResult (..))` so your new constructors don't clash with `Term`'s.)

Notice that almost every case of the new evaluator just passes the environment along unchanged. That's plumbing again. Could a monad hide it, the way `Counted` hid the counter?

**Write simplifiers.** A simplifier is a function that rewrites an expression into a simpler one, like turning `x + 0` into `x`, `x * 1` into `x`, `x * 0` into `0`, or `2 + 3` into `5`. Try writing each rule as its own small function of type `Expr -> Expr`. Because they're just functions, you can combine them with `.`. Some things worth playing with:

- Does the order you compose them in matter?
- A rule that only looks at the top of an expression misses anything nested. How would you apply a rule everywhere in an expression?
- When should you stop simplifying? Is one pass ever not enough?

**Ask whether it's correct.** A simplifier should never change what a program means. Evaluate a few expressions before and after simplifying and compare. Then think about `0 * (1 / 0)`, or `0 * y` when `y` isn't defined. Is your simplifier still correct? What would you do about it?
